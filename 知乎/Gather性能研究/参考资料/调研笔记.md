# Gather / Scatter 性能研究：调研笔记

资料访问日期：2026-10-28。本笔记整理公开来源、结论边界与架构设计讨论，区分文档事实、论文结果和条件性推导；第 38 节另行直接核验了 NVIDIA 官方网页。各节保留访问限制与未核实事项。本文为研究资料，完整初稿见[正文](../正文.md)。

## 研究问题与术语边界

- GPU SIMT 中每个线程访问不同地址，何时仍可合并访问，何时因地址分散降低效率？
- Gather / Scatter 的代价如何受事务粒度、缓存、并发 miss、内存通道与排队影响？
- 昇腾 950 与昇腾 910B 的 Gather / Scatter 应按具体接口和内存层级分别核实。
- 研究对象为昇腾 910B 与 950。
- 普通 scatter 与 atomic scatter-add 分开讨论，不能混用性能结论。

## 1. NVIDIA CUDA Best Practices Guide

来源：[Coalesced Access to Global Memory](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory)

适用架构 / 内存层级：NVIDIA CUDA GPU 的 global memory（GM）合并访问；下述 32B sector 示例依赖指南中对应架构、访问宽度与对齐条件，不代表全部历史 GPU。

已证实内容：

- 连续 32 个 float 对应 32 个不同地址，仍可合并访问。理想对齐情况下，128B 有效数据覆盖 4 个 32B sector。
- 若同样的线程访问分散到 32 个 sector，事务中有效数据所占比例下降。每线程地址不同本身不是性能差的充分条件。
- 缓存、可并发的 miss 和实际 DRAM 请求仍会影响最终性能。

不能推出的结论：

- 不能由 4 个 sector 增至 32 个 sector，直接断言运行时间必然慢 8 倍。
- sector 数量不能不经缓存与下游请求分析就等同于 DRAM 事务数或实际 DRAM 流量。

## 2. Spatter: A Tool for Evaluating Gather/Scatter Performance

来源：[arXiv:1811.03743](https://arxiv.org/abs/1811.03743)；正式 MEMSYS 2020 版本为 Patrick Lavin 等的 [Evaluating Gather and Scatter Performance on CPUs and GPUs](https://www.lavin.cc/publication/spatter)。

适用架构 / 内存层级：论文测试的 CPU / GPU 平台及索引访存 benchmark，GPU 包括 K40c、Titan Xp、P100、V100；具体缓存状态、工作集和数据路径应随实验配置说明。

已证实内容：

- 提供用于评估 Gather / Scatter 的索引访问 benchmark。
- 可用于研究访问模式与测试方法，帮助构建可复现的模式对比。

不能推出的结论：

- 不能把论文历史平台上的测量数值直接作为现代 GPU 或昇腾硬件的性能结论。
- 不同输入模式或测试条件下的数值不能直接合并为统一的 Gather / Scatter 性能倍数。

## 3. MDM: The GPU Memory Divergence Model

来源：[MICRO 2020 论文 PDF](https://microarch.org/micro53/papers/738300b009.pdf)，作者 Lu Wang、Magnus Jahre、Almutaz Adileh、Lieven Eeckhout。

适用架构 / 内存层级：基于模拟及 GTX 1080 的 GPU 存储系统研究，涉及 L1、并发 miss 跟踪、NoC 和 DRAM；平台参数以论文为准。

已证实内容：

- 不规则访问的代价不限于有效带宽下降。
- 不规则访问还可能耗尽并发 miss 跟踪能力，引起 L1 blocking，以及 NoC / DRAM 排队。

不能推出的结论：

- 不能把论文的 MSHR 数、容量、阈值和其他固定参数当作现代 GPU 规格或泛化到所有 GPU。
- 不能仅根据地址分散就断言每个工作负载都由同一种队列或跟踪资源限制。

## 4. Performance Impact of Memory Channels on Sparse and Irregular Algorithms

来源：[arXiv:1910.03679](https://arxiv.org/abs/1910.03679)

已证实内容：

- 研究稀疏 / 不规则算法性能与内存通道组织及小请求粒度的关系。
- 对这类访问的分析不能只看峰值带宽。

不能推出的结论：

- 不能直接用 Pascal 上的结果预测其他 GPU 或 NPU 的绝对性能。
- 不能忽略工作负载与请求分布，仅按通道数给出统一性能倍数，也不能把特定观测简化为普遍线性定律。

## 8. Nsight Compute Profiling Guide：计数量纲

来源：[Quantities](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#quantities)。

适用架构 / 内存层级：NVIDIA GPU 性能分析中的 request、sector、wavefront 等计量概念；解释指标时需同时核对具体硬件单元与架构。

已证实内容：

- 不能把 sector 增长倍数直接当作耗时增长倍数。
- 不能跨层级混用请求、缓存访问和 DRAM 流量指标。

## 9. 昇腾 950PR / 950DT：避免 UB bank conflict

来源：[官方 NPU architecture 3510 UB bank conflict 文档](https://asc.gitcode.com/guide/operator_practice/simd_operator_optimization/memory_access/avoid_ub_bank_conflict/avoid_bank_conflict_npu_arch_3510.html)。来源版本：asc-devkit master 预览，commit `dc9f009438d2`；预览文档可能更新，结论限于所核实版本。

适用架构 / 内存层级：文档明确的 950PR / 950DT，SIMD UB Gather / Scatter 路径。

已证实内容：

- UB 容量为 256KB，包含 16 banks / 8 groups，每个 bank 包含 4 个 8B subbanks。
- 文档说明同一 bank group 每拍支持两读或一读一写，不支持两写。这是 bank group 层级规则，不能表述为每个 bank 的端口数已知。
- UB gather / scatter 对同一 subbank、相同起始地址的访问可合并，不产生该类 bank conflict。
- 对同一 subbank、不同起始地址的访问会冲突。
- Gather / Scatter 也可能与连续访存或 MTE 访问产生冲突。

不能推出的结论与待核项：

- 不能套用老架构的 48 banks 描述。
- UB 访问可合并不意味着 GM scatter-add 对同地址没有原子竞争；内存层级与操作语义均不同。
- 文档一处表格描述与通则疑似矛盾，尚待核实；此处只记录清晰通则，不采用该疑似矛盾项推演访问结果。
- bank / subbank 规则本身不能给出整体 kernel 的固定减速倍数。

## 10. 昇腾 SIMT：GM 合并访问官方案例

来源：[访存合并官方案例](https://asc.gitcode.com/guide/operator_practice/simt_operator_optimization/memory_access/memory_access_merge.html)。

适用架构 / 内存层级：官方 SIMT GM 按行 Gather 示例。精确平台型号仍需按该页上下文核实；本节不将其默认归为任意具体 950 或 910B 产品。

已证实内容（官方示例报告，非本任务实测）：

- input 形状为 `20001 × 1023`，index 长度为 `核数 × 2048`，block 数为物理核数，`2048 threads/block`。
- 每个 thread 处理整行的版本耗时为 `4886.076 μs`。
- 改为 warp 内相邻 thread 访问相邻列后，耗时为 `866.103 μs`。
- 文档报告耗时降低 `82.3%`；按上述耗时比值约为 `5.64 倍`加速。

不能推出的结论：

- 不能将此案例数值泛化为所有 Gather / Scatter、所有 950 或所有 910B 的表现。
- 不能据此证明 UB Gather / Scatter 的 bank conflict 成本或 atomic scatter-add 的原子竞争开销。
- 不能将官方示例报告表述为本任务复现或本地实测。

## 11. NVIDIA GM sector 定量模型与观察指标

来源：

- [CUDA Programming Guide：Coalesced Global Memory Access](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html#coalesced-global-memory-access)
- [Unlock GPU Performance: Global Memory Access in CUDA](https://developer.nvidia.com/blog/unlock-gpu-performance-global-memory-access-in-cuda/)，2025-09-29。
- 第 1 节 CUDA Best Practices 与第 8 节 Nsight Compute 计数量纲说明。

适用架构 / 内存层级：NVIDIA CC >= 6.0 的 GM 访问模型。限定一个 warp 中 32 个活跃线程，每个线程读取不同且自然对齐的 4B 数据，基址 32B 对齐；stride 以 4B 元素计。表中覆盖字节数按 sector 数乘以 32B 计算，有效数据均为 128B。

| 访问模式 | sector 数 | sector 覆盖字节数 | 有效数据利用率 |
| --- | ---: | ---: | ---: |
| 连续，或同一连续地址集合的任意线程排列 | 4 | 128B | 100% |
| stride 2 | 8 | 256B | 50% |
| stride 4 | 16 | 512B | 25% |
| 每个 lane 位于不同 sector | 32 | 1024B | 12.5% |

已证实内容及指标用法：

- 这是 sector 工作量模型，地址集合决定覆盖范围；线程与地址的排列变化不必然破坏合并访问。
- 可观察 `l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum` 与 `l1tex__t_requests_pipe_lsu_mem_global_op_ld.sum`。
- 对满 warp、每 lane 4B 的相应访问，sectors/request 可从 4 到 32；仍须联合 L1 / L2 hit / miss、wavefront 和下层吞吐解释。

不能推出的结论：

- 32 sectors 相对 4 sectors 不保证慢 8 倍。
- sector 工作量不等于 DRAM 物理事务数，也不等于串行周期数。
- 不能不检查活跃线程数、访问宽度和 workload 混合，就用聚合指标比值套用表中利用率。
- 本模型不适用于 shared memory bank conflict 或 constant memory 不同地址的序列化。

## 12. 索引依赖、重复读取与原子更新

来源：上述 CUDA 访存资料，以及 [CUDA 13.0.2 Programming Guide：SIMT Architecture](https://docs.nvidia.com/cuda/archive/13.0.2/cuda-c-programming-guide/index.html#simt-architecture)。

适用架构 / 内存层级：CUDA SIMT 的索引读取与内存更新语义；具体性能需按接口与硬件验证。

已证实内容与分析边界：

- `x[index[tid]]` 存在索引 load 到数据 load 的依赖，不能只按最终数据地址的 sector 覆盖分析全部延迟。
- 重复读取没有原子更新竞争，不能与重复目标地址的 atomic scatter 混为一谈。
- 不同位置的 scatter 与重叠更新的 atomic scatter 是不同操作。
- GM sector、shared bank、constant memory 不同地址序列化属于不同路径，不能共用同一个性能模型。

不能推出的结论：普通非原子写入的访问规则不能证明重叠写入正确，也不能预测 atomic scatter-add 的竞争成本。

## 13. 架构讨论要点，待文档核验

来源：架构讨论；以下是待核实问题，不是已证实的芯片规格。

适用范围：GPU 与昇腾 910B / 950，需按架构、接口与内存层级分别核验。

- 合并访问的窗口与粒度：哪些线程、请求或指令能够共同合并，合并单位是什么？
- cacheline 宽度，以及每周期可同时查询几条 line 的 tag：区分 line、sector、request 与 tag 查询吞吐。
- buffer 路径的 bank 数、地址到 bank 的映射，以及每 bank 的读写端口数。
- 端口语义：1R1W 与 2R 不同，不能将一个读端口加一个写端口当作两个读端口。
- 当访问集中到同一 bank 时，核实冲突与串行服务条件，包括端口能力、访问宽度、地址以及硬件合并或广播规则。

不能推出的结论：未经公开资料或可靠测量确认，不填写具体芯片的 tag 查询数或 bank 端口数；不能仅凭 bank 数计算固定性能倍数。

## 16. 昇腾 950PR 原子优化：histogram 案例

来源：[原子指令优化](https://asc.gitcode.com/guide/operator_practice/simt_operator_optimization/instruction_optimization/atomic_instruction_optimization.html)，master 预览文档，页面明确 msOpProf / 950PR。

- 不能将收益解释为普通 scatter / gather 的性能差异。
- 页面“原子次数相同”文字与代码不一致，不以该文字作为结论；需区分 GM 与 UB 原子次数。

## 18. 避免 bank 冲突：原则与候选论文

### 已核实原则与适用边界

来源：第 9、15 节官方 UB 文档，以及 [NVIDIA CUDA Programming Guide](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html) 中 shared memory 的 `32 × 33` padding 示例。下述资源约束推理不等于具体芯片规格。

| 方法 | 作用与适用范围 | 成本或限制 |
| --- | --- | --- |
| padding | 改变规则布局的行步长和 bank 映射，适合转置等可预测模式 | 增加容量占用；不是任意随机索引的通解 |
| swizzle / XOR 映射 | 改变逻辑地址到 bank 的映射，尝试分散有结构的冲突 | 需验证实际访问分布、映射开销和硬件支持；不能保证任意索引无冲突 |
| 请求跨拍重排 | 将争用同一服务资源的请求安排到不同拍 | 引入调度、缓冲和等待；没有凭空增加单 bank 吞吐 |
| 重复读广播 / 合并 | 在硬件支持时合并同一地址的读取 | 不能套用到不同地址，也不能套用到写入或原子更新 |
| 复制数据 | 将同一数据放到不同 bank，增加可选择读取位置 | 占用额外空间；更新需要维护副本一致性 |
| 增加端口 | 增加物理并发服务能力 | 涉及面积、功耗、时序或实现复杂度，不是软件指令替换 |

在“单 bank 单读口”的假设下，同拍对多个不同地址的读取不能仅靠更换 Gather 指令就消除资源瓶颈，需要跨拍服务、改变映射、复制数据或增加端口等方式承担成本。相同地址读取可由硬件广播的情况是例外；写入和 atomic 需另行分析。这里没有宣称任何目标芯片实际采用单读口。

不能推出的结论：单个 padding 案例的收益不能推广为所有 Gather 的优化收益；尚未核实的 swizzle 或调度方案不能表述为目标硬件已经支持。

## 25. bank 冲突优化：新增证据与模型边界

资料访问日期：2026-10-28。以下记录已核实的来源及其适用范围。

### NVIDIA padding 与 TMA swizzle

来源：

- [Shared Memory in Matrix Multiplication C = AAT](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#shared-memory-in-matrix-multiplication-c-aat)
- [Shared Memory Bank Swizzling](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html#shared-memory-bank-swizzling)

已证实范围：32×33 padding 相对 32×32 增加容量 `(33-32)/32 = 3.125%`，这是该布局例子的推导。TMA 的 128B swizzle 示例适用于 CC 9.0+ 的结构化 tile。

不能推出的结论：特定 tile 的 padding / swizzle 不保证任意随机 Gather 无冲突；容量增长比例也不是一般优化方案的统一成本。

### Configurable XOR Hash Functions for Banked Scratchpad Memories in GPUs

来源：[TU Eindhoven 作者门户](https://research.tue.nl/en/publications/configurable-xor-hash-functions-for-banked-scratchpad-memories-in/)。IEEE Transactions on Computers 65(7), 2045–2058，2016；DOI：10.1109/TC.2015.2479595。

取证范围：IEEE 正文受限，作者门户摘要已核实。摘要报告 Fermi-like 模拟、22 个 benchmarks 与 24% 性能收益。

不能推出的结论：这是历史模拟摘要结果，不是现代 GPU 实测；不扩写正文不可读的映射实现、实验细节或普适收益。

### Sorting and Permuting without Bank Conflicts on GPUs

来源：[2015 论文](https://arxiv.org/abs/1507.01391)。

已核实范围：研究 DMM 理论模型，涉及离线预处理与多阶段调度。

不能推出的结论：不能把算法阶段上的无冲突组织表述为任意 Gather 可在单拍完成，也不能省略预处理和调度成本。

### Eliminating Bank Conflicts in GPU Mergesort

来源：[SPAA 2025 论文 PDF](https://algoparc.ics.hawaii.edu/pubs/p25-spaa.pdf)，Kyle Berney、Nodari Sitchinava；DOI：10.1145/3694906.3743337。

适用范围：RTX 2080 Ti / CUDA 11，Mergesort 中结构化的 dual-subsequence gather。

已核实内容：随机输入表现接近 Thrust，主要改善构造的坏输入。

不能推出的结论：不能作为任意 Gather 的普遍加速结论，也不能把结构化子序列条件省略。

### 简化服务下界：分析推导，不是芯片规格

假设已将可广播的重复 word 合并，bank b 有 n_b 个独立读请求，每 bank 每拍最多服务 r_b 个，且 r_b > 0，各 bank 可并行服务。则所需服务步至少为 `max_b ceil(n_b / r_b)`。

该式只给出理想化下界；group 约束、依赖、端口类型和竞争会增加实际服务时间。不能由此反推未公开的芯片端口数。仅重新排列 lane 编号而不改变同一轮地址集合，不会降低该模型中的冲突。

## 26. 应用案例：DeepSeek CSA 与 KV 索引访问

来源：

- [DeepSeek V4 官方 model card](https://fe-static.deepseek.com/chat/transparency/deepseek-V4-model-card-EN.pdf)，第 2 页 Model properties。
- [NVIDIA TensorRT-LLM：DeepSeek V4 on Blackwell](https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog26_DeepSeek_V4_on_NVIDIA_Blackwell_Model_Specific_and_Agentic_Workload_Optimizations_in_TensorRT-LLM.html)

已核实内容：

- CSA 沿序列压缩 KV 后应用 DSA；HCA 是重压缩后 dense attention 的另一路，不能把 CSA 全部改称 DSA。

- gather 语义不要求物化独立的 gather 输出；实现可能通过融合 kernel 直接读取所选 KV 并计算 attention。
- 不能仅凭有 Gather 就断言整体 attention 很慢，需考虑条目内连续性、压缩、选择开销和 kernel 组织。
- 不能把上述语义直接当作某一具体指令或 bank 冲突模式。

## 34. CPU 综合分析与取证限制

以下为结合资料的分析推论，不是新增硬件规格：

- 有效数据字节、独立 cacheline / page 数、实际流量分别记账。
- `index load → 地址生成 → data load` 的依赖可能限制提前发起请求。

候选优化及需计入的成本：

| 优化 | 需核算的代价 |
| --- | --- |
| 连续 load + permute | 额外读取、排列指令与寄存器压力 |

## 35. 从任意索引 Gather 到可预测 ND DMA

记录类别：架构讨论与推导。设计设想、推导条件和公开文档事实分别列出；未运行基准，不是已实现硬件的性能声明。

### 架构讨论与模型前提

设想一个五六维 ND DMA，各维长度 L_d 与字节 stride s_d 可配置，至少某一维连续。逻辑元素地址可表示为：

`addr(i_0, …, i_(D-1)) = base + Σ_d i_d × s_d`，其中 `0 <= i_d < L_d`。

这类多维 load / store 可视为结构化 Gather / Scatter：地址由规则生成，不必逐元素读取任意索引。规则步进不等于每一维都在物理内存中紧密连续；是否连续需结合元素宽度、stride 与维度长度判断。

### 可考虑的硬件优化：有条件的推导

| 方向 | 机制与收益机会 | 前提与成本 |
| --- | --- | --- |
| 描述符 / 递增计数器 | 描述各维长度与 stride，以计数、进位和增量地址生成替代逐元素索引 load 与通用地址计算 | 仍需描述符设置、边界处理和地址生成硬件；不是零成本 |
| 连续维折叠 | 将连续维和满足 stride 条件的相邻维组合成较长 burst | 对紧密正向布局，内维元素步长等于元素宽度，外维 stride 等于内层跨度时可合并；接口长度、对齐、页与保护边界仍限制实际拆分 |
| line 边界预判 | 提前确定请求覆盖范围，合并同 line 请求，提高有效数据利用率 | 同 line 合并需保留操作语义；不能将请求合并等同于固定 DRAM 事务数 |
| bank 周期分析 | 在已知 bank 映射下，由 stride 推导访问分布与冲突周期 | XOR / swizzle 等映射需要相应分析，不能一律套用简单取模公式 |
| 跨行 / 块交织 | 调整每轮请求集合，让不同 bank 更均匀服务，再重组为逻辑顺序 | 需要调度、缓冲和顺序标签；受到依赖与可重排范围限制 |
| 目的 buffer 布局协同 | 写入时采用 padding / swizzle，使布局同时服务搬运与后续消费 | 需要消费者使用相容布局；会增加容量、映射或布局转换成本 |
| prefetch / 并发请求 | 利用未来地址可预测性提前发请求，隐藏部分延迟 | 受未完成请求容量、缓冲、带宽和同步限制；可能产生无效预取或污染 |

源与目的应分别分析：源端连续读取不保证目的 buffer 无冲突，目的端均匀分布也不保证源端请求高效。读写及搬运 / 消费并行时，还要计入共同资源竞争。

### 不变的约束与下界

- 结构化访问不保证无冲突；若多个不同 word 仍集中同一 bank，仍受第 25 节端口服务下界约束。
- 仅调整 lane 编号、而不改变同轮地址集合，不能改变该模型下的冲突集中程度。
- 对 store，别名、重叠地址、可见性和顺序要求限制重排；不能用读路径的广播或合并规则代替写入语义。
- 对重复地址、atomic 或有跨元素依赖的操作，需先确定允许的合并与重排语义。
- 是否获益取决于可折叠连续长度、stride、冲突周期、队列容量、重组成本及后续消费者；不推导固定加速倍数。

### 公开工程例：NVIDIA TMA

来源：[CUDA Programming Guide 13.2.1：Asynchronous Data Copies](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/04-special-topics/async-copies.html)。此处记录对应版本的文档事实。

公开文档事实：NVIDIA TMA 支持 1–5D tensor 传输，并对 stride / alignment 等提出限制。

不能推出的结论：

- TMA 不是通用 6D DMA，也不能作为任意 ND DMA 设想已经实现的证明。
- 上述计数器、bank 预测、跨行交织与重组属于架构推导，不能未经文档证据就称为 TMA 的内部实现。
- TMA 的支持范围不代表 GPU、昇腾或其他 DMA 的共同能力；平台限制需逐项核实。

### 补充讨论：将仿射地址描述符作为加速器接口

类别：架构设想与分析推导，不是已证实产品实现。

当一次任务的 base 与各维 stride s_d 固定时，`addr = base + Σ i_d × s_d` 关于坐标 i_d 是仿射表达式，即一次多项式（退化情形可为常量）。固定系数是这个判断的前提，不能把任意随坐标变化的 stride 也归为同一模型。

若加速器直接接受维度长度与 stride 描述符，就能保留索引结构，相比先展开成显式 index tile，可省去相应索引的生成、存储和读取，并更容易预规划连续段、cacheline 边界、bank 冲突周期与跨行交织。这里的优势是无需先从离散地址流中重新识别已经由描述符给出的规则；实际收益仍取决于任务规模、描述符开销和硬件实现。

比较边界：普通 Gather 也能流式处理索引，并在动态窗口内识别可合并请求，不要求先物化完整 index tile；不能断言其永远无法发现访问规律。描述符只是显式提供优化机会，仍需真实的地址规划、请求调度、缓冲与执行能力，不能消除固定 bank 端口的服务下界，也不能放宽 store 别名和顺序约束。

### 补充讨论：ND DMA 的参数配置、ISA 与启动摊销

类别：架构讨论与推导。讨论以昇腾 ND-DMA 为背景，并用每维五参数、三维十五参数举例，提到 base、stride、burst length、padding 等。这里记录的是示意模型；真实产品字段、编码方式以及 base 是否每维独立尚未核实，不能当作昇腾手册事实。

#### 讨论重心修正：完整参数绑定优先

按本文的设计要求，SuperScalar NPU 的 TMA 是乱序操作。每项操作须先绑定完整、确定的参数版本，再进入可乱序执行状态；执行时不能读取被后续操作改写的公共配置。核心是高效构造完整参数，以及多个在飞操作的隔离、生命周期和依赖管理。以下配置复用与摊销仅是满足这一要求后的优化方向，不能代替完整参数绑定。

#### 配置与启动接口的候选方案

- 不变参数预置复用：让尺寸、固定 stride、布局等在一组任务中保持配置，仅更新每次变化的 base 或边界；适用性取决于实际变化集合。
- descriptor 指针或 ID 加动态参数：通过描述符选择静态配置，再以少量动态值触发传输；需要承担描述符存储、获取、定位和可能的缓存成本。
- 批量参数加载：一次指令或一组打包操作传入多个字段；减少显式配置指令并不自动减少读取字节或传输周期。
- 编译期构造：提前构建静态描述符和参数模板，在运行时实例化动态字段；不能把运行时不确定信息也假定为编译期常量。

这些是 ISA / 加速器接口的设计方向，不是已经核实的产品功能。

#### 配置开销的示意计算

假定三维共有十五个独立配置参数，每个参数恰好用一条写入指令，一次 launch 恰好一条指令：

- 单次完整配置与启动：`15 + 1 = 16` 条指令。
- 配置不变、复用 R 次且 `R >= 1`：总共 `15 + R` 条，平均每次 `1 + 15/R` 条。

该计数不含参数的数据准备、描述符分配 / 获取、动态字段更新、同步或完成处理。若每次需要修改字段，其成本必须另计；若硬件提供批量配置，单参数单写假设也不再成立。

必须分清四个量：参数个数描述接口信息项，指令数描述编码与执行组织，配置字节描述实际信息传输量，启动延迟描述配置到请求开始推进的时间。它们之间不存在未经实现验证的固定比例。

#### 异步任务与配置生命周期

- 明确操作参数的绑定点：进入可乱序执行状态前须确定完整有效版本。可复制快照，也可绑定保持有效的不可变描述符版本；即使稍后才读取描述符内容，也不能让该版本被后续操作改写。
- 明确更新与回收时机：不能在异步任务仍可能读取某个描述符时原地修改或复用其存储；可考虑不可变版本、独立实例或受完成事件约束的复用。
- 多描述符在飞需要配置隔离和任务身份，防止后一次更新改变前一次任务的地址、长度或布局。
- 明确依赖、数据可见性及完成通知的含义，区分已发出、配置已捕获、搬运已完成以及消费者可安全访问。
- 避免依赖隐式共享配置寄存器而要求所有任务串行配置和完成；若确需共享配置，必须规定快照、版本或排他规则及其并发代价。

这些正确性条件决定配置复用是否安全，也决定减少指令数能否转化为实际并发和启动收益；未测量前不声称任何固定启动延迟或吞吐提升。

## 36. 本文设计要求：乱序 TMA 的完整参数与多在飞隔离

类别：本文对 SuperScalar NPU 提出的设计要求，尚未验证具体实现。

每项操作必须先绑定完整确定的 base / stride / length / padding 参数版本。ISA 的任务是高效构造和传递这组完整状态，并保证操作执行不受后续配置更新影响；不能仅以参数复用或“少配置几个字段”回答该问题。

需要明确的接口条件：

- 参数依赖：所有必需字段就绪后，形成该操作的完整有效参数状态；静态模板与动态字段如何组合必须确定。
- 版本与身份：每个在飞操作关联确定的参数版本和任务身份。快照、不可变版本或其他隔离机制均为候选设计，未指定某个方案已经实现。
- 生命周期：确定构造、绑定、允许执行、完成和回收的边界；后续更新生成新版本或受合法回收条件约束。
- 数据依赖：完整参数不等于数据依赖已经满足，仍需判断源数据就绪、目的覆盖、别名及顺序约束。
- 完成语义：区分参数已捕获、传输已结束、写入已可见和消费者可安全使用；避免把这些状态合并为含义不清的“完成”。
- 并发：避免由可变公共配置造成任务互相污染，或要求本可并行的操作串行配置与执行。

完整参数绑定不意味着每次必须重复写入所有静态字段，但任何复用都必须使该操作获得完整、确定且生命周期安全的版本。前述 `15 + R` 仅在配置不变并可安全复用的示意条件下成立，不包含版本管理等成本，不是乱序 TMA 的一般指令计数。

## 37. GPU 已有 SIMT，为什么引入 TMA

来源：[NVIDIA Hopper Tuning Guide §1.4.1.2](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html)，结合第 35 节 CUDA 13.2.1 async copy 文档。此处记录对应公开资料的能力范围。

适用范围：NVIDIA Hopper TMA 的公开搬运能力与编程动机；不是本文 SuperScalar NPU 的乱序执行规范。

公开文档支持的工程动机：

- SIMT 可以表达数据搬运和 Gather，但逐线程组织搬运需要占用相关指令与寄存器资源。TMA 面向可描述 tensor 传输，将部分搬运组织工作交给专用机制。
- TMA 避免寄存器中转，减少 SM 侧搬运指令，可由单线程发起较大的 1–5D 传输。
- 异步搬运可与计算重叠，并支持 warp specialization，让负责搬运与负责计算的线程束分工。

分析推论：TMA 的价值包含降低搬运的指令和资源开销、利用已知布局组织传输以及实现计算重叠；不是因为 SIMT 无法表达 Gather。小传输或配置 / 同步占比较高时，收益仍需测量。

不能推出的结论：

- Ampere cp.async 已有部分绕过寄存器的异步复制能力，不能声称 TMA 首次或唯一支持异步搬运 / 绕寄存器。
- TMA 针对符合描述能力和接口约束的 tensor 搬运，不能替代任意随机 Gather。
- NVIDIA 异步 TMA 不等同于本文设想的乱序 TMA。异步发起与计算重叠不能证明相同的乱序调度、参数绑定、依赖或完成语义。
- 本节没有提供或验证跨平台加速倍数。

## 38. TMA / SIMT 常见分工与受限 tensor Gather

### 讨论结论：主要适用模式，不是绝对边界

讨论中的常见分工是“TMA 做规则 strided load，SIMT 做不规则离散 Gather / Scatter”。SIMT 也能执行规则访问；TMA 对维度、shape、stride、alignment 和搬运方向等有限制，并非所有 strided 访问都能高效映射。

引入 TMA 的动机仍是第 37 节所列的搬运指令 / 寄存器资源开销、较大 tensor 传输和异步计算重叠。保留 Hopper Tuning Guide 来源及 Ampere cp.async 更早已有部分异步、绕寄存器能力的边界。

### 本地直接核验的官方 PTX 事实

来源：[PTX ISA 9.4：cp.async.bulk.tensor](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-cp-async-bulk-tensor)，同时读取该页 §5.5.3.4 与 Target ISA Notes。此节已直接浏览官方网页核验。

- `.tile::gather4` / `.tile::scatter4` 自 PTX 8.6 引入，仅针对二维 tensor 的四行访问，不支持 interleave，仍受 tile 模式约束。
- gather4 汇集源 tensor 的四行；scatter4 将数据分发到目的 tensor 的四行。
- gather4 以 `.shared::cta` 为目的要求 `sm_100` 或更高；以 `.shared::cluster` 为目的要求 `sm_100a`，PTX 8.8 起还支持 `sm_100f`。
- scatter4 的目标支持明确列出 `sm_100a`、`sm_101a`（PTX 9.0 起改名 `sm_110a`），以及对应 `sm_100f` / `sm_101f`（后改名 `sm_110f`）族支持；不能简写为任何 `sm_100+` 均支持所有形式。

这些是受限的 tensor 行搬运，不是任意每 lane 标量地址访问。坐标维度文字存在不同段落表述差异，本节不据概述生成调用代码；真实调用需核对具体指令语法与版本修订。

### CSA 路径：条件性分析

CSA 索引选择整条连续 KV 行 / 块时，条目之间离散、条目内部连续，有可能评估受限 tensor Gather 或 SIMT / TMA 混合路径。是否合适取决于行布局、分组、传输粒度、目标架构和融合实现；这里没有确认某个 CSA kernel 实际采用 gather4。

不能从“有离散索引”直接推导“只能逐 lane 随机 scalar”，也不能从 TMA 存在 gather4 推导任意 CSA 都能无额外成本映射。NVIDIA 异步 TMA 与本文的乱序 TMA 设计仍需分别讨论。
