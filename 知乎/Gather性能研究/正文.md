# 为什么 Gather 有时很慢：从访存瓶颈到乱序 TMA

*技术文章初稿 · 2026-10-29*

Gather 把一组索引指向的数据收集起来，接口看起来很简单：给出地址，取回元素。GPU 可以让不同线程各自执行一次 load，CPU 可以用向量 Gather 表达多个地址，NPU 也提供不同层级的索引访存接口。但指令能够表达多少个元素，与存储系统能在同一拍服务多少个请求，始终是两件需要分别分析的事。

讨论 Gather 为什么慢，需要知道地址落在哪里、数据经过什么路径，以及执行前还要准备什么。外存访问可能浪费事务中的有效载荷，也可能受标签查询、未完成请求容量或地址依赖限制；数据进入片上 Buffer 后，又可能集中到少数 bank。若再把搬运交给 ND DMA 或 TMA，数据路径会变得更专用，参数构造与任务调度则成为新的成本。

本文沿这条路径展开。厂商能力依据公开文档，定量例子保留适用条件；后半部分关于 SuperScalar NPU 的乱序 TMA 是架构设计要求与推导，尚无实现测量或 PPA 结论。

## 一、地址不同，并不意味着访问不能合并

假设一个 warp 的 32 个线程分别读取 `x[0]` 到 `x[31]`。每个线程的地址都不同，但这些 float 恰好组成连续的 128B 数据。若基址适当对齐，硬件可以用少量请求覆盖全部数据。即使交换线程和元素的对应关系，只要同轮访问的地址集合保持不变，覆盖的存储区域也可以不变。

真正需要比较的是另一种情况：32 个线程各读 4B，却分别落在 32 个相距很远的区域。有效数据仍然只有 128B，存储系统需要处理的地址和传输单元却多了。SIMT 允许线程产生不同地址，并不自动消除这些地址带来的服务工作量。

以 NVIDIA 计算能力 CC≥6.0 的 global memory 合并访问模型为例，限定 32 个活跃线程、每线程读取不同且自然对齐的 4B、基址 32B 对齐，得到以下覆盖关系。这里 stride 以 4B 元素为单位。[CUDA Best Practices][cuda]

| 同一 warp 的地址分布 | 32B sector 数 | sector 覆盖字节 | 有效数据比例 |
| --- | ---: | ---: | ---: |
| 连续，或同一连续集合的任意线程排列 | 4 | 128B | 100% |
| stride 2 | 8 | 256B | 50% |
| stride 4 | 16 | 512B | 25% |
| 每个线程位于不同 sector | 32 | 1024B | 12.5% |

这张表解释了地址分散为什么可能降低效率，也限定了结论：4 到 32 sectors 是八倍覆盖工作量，不能直接写成八倍运行时间。缓存可能已经持有部分数据，请求可能并行推进，下游也可能合并或采用不同事务组织。sector、cacheline、DRAM 物理事务和执行周期不能互换。

![连续访问与离散访问的 Sector 覆盖量](图片/sector.png)

*图 1：同样读取 128B 有效数据，触及的 32B sector 可从 4 个增加到 32 个；覆盖量的八倍差异不代表耗时增加八倍。*

Scatter 还要多看一层语义。写入互不重叠的位置，与多个线程对同一位置执行原子加法，可能具有完全不同的瓶颈。重复读取存在合并或广播机会，重复更新则需要维护正确的更新结果。把普通 Scatter 与 atomic scatter-add 放在同一张性能表里而省略这个条件，往往会把原子竞争误算成离散地址的代价。

## 二、Cache 路径的限制，远不止有效带宽

合并访问有自己的窗口。硬件在某个请求边界内看到一批地址，并据此形成访问，不能假定任意时刻出现的地址都会被无限期收集、排序，再用全局最优方式发出。因此，同样的地址集合，若被拆到不同指令或不同批次中，仍可能形成不同的请求组织。讨论合并能力，必须同时说明参与的线程、访问宽度和硬件能够共同处理的范围。

请求形成后，还要查询 Cache。cacheline 定义缓存组织的空间范围，实际查询、填充和传输还可能细分到 sector；tag 查询能力决定每拍能够检查多少条独立 line，数据阵列与返回通路又限制能够送回多少数据。扩大 line 可能有利于连续访问，却不能凭空增加独立地址的标签查询能力；如果每条 line 只取一个 word，宽 line 还可能携带更多暂时用不到的数据。

这里可以做一个纯模型推导：假设一批访问需要 Q 次独立标签查询，相关查询通路最多每拍接受 p 次，那么至少需要 `ceil(Q/p)` 个查询服务步。实际时间还受 bank、流水线、合并和缓存状态影响。这个式子说明为什么需要追问 tag 并行服务能力，并没有给任何芯片填入未公开的 p。

Cache miss 之后，系统还要保存未完成请求的状态。请求越分散，越可能消耗更多 miss 跟踪项、下游队列和返回缓冲；当某种资源满了，即使 DRAM 带宽尚未打满，前端也可能停止接收新请求。MDM 在其模拟与 GTX 1080 研究范围内讨论了这种 memory divergence，包括 L1 blocking、NoC 与 DRAM 排队。论文中的容量参数属于对应平台，机制可以用于分析，数值需要重新核实。[MDM][mdm]

如果地址还跨越很多 page，TLB 和 page walk 也会加入关键路径。对 `x[index[i]]` 而言，数据地址依赖索引 load 的结果：索引没有回来，最终数据请求就无法按原路径发出。增加数据带宽并不能直接解除这条依赖。CPU 上还要考虑 load/store 端口、fill buffer、store buffer 与写入所有权；GPU 和 NPU 则应按各自路径检查对应资源。

CPU 手册给出了一个有边界的例子：Neoverse V2 的 128-bit SVE/SVE2，在所列 L1 命中条件下，连续 LD1* 形式的延迟为 6 cycles、最高吞吐为每周期 3 条，32-bit scaled-offset Gather 则为 10 cycles、每周期 0.5 条，并占用 L 与 V 管线。这只能说明该微架构和寻址形式的差异，不能把吞吐比当成任意程序的加速比。[Neoverse V2 SOG][v2]

AVX2 有 Gather，没有通用 Scatter；AVX-512 增加相关能力后，收益仍依赖实现。Spatter 在 Broadwell、Skylake 和 KNL 上观察到不同的向量化收益，部分 Broadwell 模式甚至变慢。其有效 double 带宽不计 index 流量，也就不能直接作为 DRAM 实际带宽。测试 Gather 时，向量宽度、掩码、索引局部性、缓存状态及微码环境都属于结果的一部分。[Spatter][spatter]

因此，仅看到“带宽低”还不足以定位问题。有效载荷利用率、请求生成与服务能力、未完成请求数量，以及依赖链上能够提前推进的工作，需要一起看。Nsight Compute 区分 request、sector 和 wavefront，正是为了避免把这些层次压成一个数字。[Profiling Guide][nsight]

## 三、数据已经在 Buffer，为什么仍然会排队

GPU shared memory、昇腾 UB 这类显式管理的片上缓冲，减少了对外存访问的依赖，但仍有物理服务约束。讨论 Cache 时关注的标签和 miss 路径，在 scratchpad 上往往转化为地址到 bank 的映射、bank 内部读写能力，以及多个 bank 共用的 group 通路。

假设某个 bank 每拍只能读一个独立 word，四个请求同时命中这个 bank 的四个不同地址，就至少需要四个服务步。换一条能表达四个元素的 Gather 指令，并不会增加这个 bank 的读能力。所谓 1R1W，表示可支持的读写组合包含一读一写；它不能直接当成 2R 来使用。只有明确了端口类型和共享资源，bank 数才具有性能意义。

更一般地，先合并硬件允许广播的重复 word，令 bank b 剩余 n_b 个独立读取、每拍最多服务 r_b 个，且各 bank 可以并行、r_b>0，则服务步数至少满足：

```text
服务步数 ≥ max_b ceil(n_b / r_b)
```

这是给定服务能力下的理想下界。group 冲突、读写混合、依赖和其他访存单元的竞争会进一步增加时间。它也说明，仅把相同一轮地址重新分配给不同 lane，无法改变热点 bank 的请求数量。

*图 2：左侧展示单读口 bank 的并行与排队，右侧预示下一节的 Padding 方法；32-bank、4B word 是教学用简化模型，不代表昇腾 UB 的实际组织。*

昇腾的代际差异尤其要求分层讨论。根据 CANN 软件包对应关系，910B 归入这里讨论的 Atlas A2 范围；其官方 2201 资料描述了 192KB UB、48 banks、16 groups；950PR/950DT 的 3510 资料则描述 256KB UB、16 banks、8 groups，并进一步划分 subbank。后者还给出 group 级每拍两读或一读一写等规则。这些信息不能互相套用，group 的服务组合也不能直接推导物理 SRAM 每 bank 的端口数。[CANN 安装表][canninstall]、[2201 UB][ub2201]、[3510 UB][ub3510]

按已核实的 3510 master 预览文档（commit `dc9f009438d2`）通则，同 subbank、相同起始地址的相应访问可以合并，而不同起始地址会产生该类冲突；Gather/Scatter 还可能与连续访问或 MTE 竞争。这个局部规则不能推到 GM 上，得出“多个线程向同址 scatter-add 没有竞争”的结论。GM、UB 和 atomic 各自有不同的资源与语义边界。

接口名称也不能替代路径分析。昇腾 LocalTensor Gather 面向局部存储，文档中每个 repeat 的处理量不能解释成每周期 GM 吞吐。[Gather API][ascgather] Triton Ascend v3.6.0 对结构化与非结构化访问采用不同编译路径，950 的混合路径在满足条件时可转 SIMT indirect load/store。具体 lowering 可以解释某段代码的成本，却不能据此断言所有 910B GM Gather 都按同一种方式执行。[Triton Ascend 架构说明][triton]

## 四、优化必须改变资源的使用方式

Padding 对规则访问很有效。NVIDIA 的矩阵转置相关示例将 shared memory tile 从 32×32 改为 32×33，改变行步长，使按列访问不再以相同方式集中到 bank。这个例子的容量增加为 1/32，即 3.125%。收益来自布局与访问模式之间的关系；给任意随机索引统一补一列，并不能保证得到相同结果。[CUDA shared memory 示例][padding]

Swizzle 或 XOR 映射也是调整地址分布，但需要结合消费者的模式选择映射。TMA 的 128B swizzle 示例针对受支持的结构化 tile。公开 [XOR 研究][xor]中的历史模拟、[排序置换的 DMM 理论][dmm]，以及 [Mergesort 中特定子序列 Gather][mergesort]，分别依赖不同前提，不能合并成“随机访问总能无冲突”的结论。一个布局可能改善按列读取，却增加另一种访问或地址计算的成本。[TMA swizzle][swizzle]

另一类方法保留布局，改变每拍发出的集合。先检查若干索引，把落到不同 bank 的请求编到同一批，再在返回端恢复逻辑顺序，就有机会提高每批的服务并行度。不过，索引分析、等待凑批、缓冲和结果归位都要付费。如果所有请求都落到一个单读口 bank，重排能够改变次序，却无法缩短该 bank 的最低服务时间。

对于重复读取，广播可避免重复服务同一个 word；对于只读热点，也可以把副本放到不同 bank，增加读取位置的选择。前者依赖硬件合并规则，后者消耗容量和初始化带宽。数据一旦频繁更新，还需要维护副本一致性。增加真实端口则把成本放到面积、功耗和时序上，不能作为无成本的软件修补。

CPU 的连续 load 加 permute、按局部性分桶、blocking 和提前读取索引，也是在调整同样的资源关系。SPC5 使用分块连续读取配合 AVX-512 expand 或 SVE compact，但块填充率不足时可能不如 CSR；这体现了格式与算法的整体取舍。Arm 的重复索引直方图示例还需要 HISTCNT 等处理，Scatter 本身不会自动完成原子归约。[SPC5][spc5]、[SVE Programming Examples][sveexamples]

优化是否有效，最后取决于减少的访存工作，能否覆盖预处理、逆置换、寄存器压力、缓存污染和维护成本。即使重排使访问更均匀，浮点归约顺序、重叠写入与可见性要求也可能限制它的使用。结构稳定、能够反复利用的模式，通常比一次性的任意索引更容易摊销这些成本。

## 五、CSA 中的 Gather：离散发生在哪一维

DeepSeek CSA 提供了一个更接近实际应用的例子。V4 model card 将 CSA 定义为 Compressed Sparse Attention：沿序列压缩 KV 后应用 DSA；HCA 则是重压缩后进行 dense attention 的另一路。结合公开实现说明，可以沿着“索引选择→选中压缩 KV 条目→Attention 消费”理解其访存，压缩历史与 local window 共同构成需要处理的数据。[DeepSeek V4 model card][deepseek]、[TensorRT-LLM 实现说明][trt]

这里的离散主要发生在条目选择上。TopK 选出的 token 或压缩条目可以相距很远，但每个 KV 条目内部沿 head 维仍可连续。于是，同一批访问同时包含两种性质：块间离散，块内有连续载荷。把它简化成每个 lane 都在随机读取一个 scalar，会丢掉最有价值的结构信息。

![离散 KV 条目选择与条目内部连续载荷](图片/blocks.png)

*图 3：以索引 [1, 6, 3] 示意条目选择，收集后保留索引顺序；图中连续布局取决于实现，紧凑 Buffer 也可以由融合 kernel 的直接消费路径替代。*

Gather 语义也不要求先生成一个独立中间张量。实现可以先收集选中条目，再计算 Attention；也可以在融合 kernel 中直接读取所需 KV 并消费。前者增加中间结果的写入与读取，后者需要把索引、搬运和计算调度放到同一执行过程里，各有容量和流水安排上的约束。

分析 CSA 的性能，需要分开核算 TopK 选择、压缩、条目搬运和计算。整条连续 KV 行可能适合受限 tensor Gather 或混合路径，但实际是否采用某条指令，需要实现证据。仅凭程序包含 Gather，无法判断整个 Attention 很慢；真正要追问的是，算法留下的连续性有没有一直保留到硬件接口。

## 六、仿射 ND DMA：让硬件直接看到地址规律

再看一个多维 load：每维长度和 stride 都能确定，至少一个内层维度连续。它在逻辑上同样收集分布在不同位置的数据，但地址不必来自任意索引表。若任务内 base 和各维 stride 固定，则地址可以写成：

```text
addr(i₀, …, iD₋₁) = base + Σ i_d × s_d
0 ≤ i_d < L_d
```

这里 L_d 是维度长度，s_d 是字节步长。关于坐标 i_d，这是一个仿射表达式，也就是带常数项的一次多项式。维度可以规则递增，却未必在物理地址上紧密连续；连续性仍由元素宽度、长度和 stride 的关系决定。

如果先把这些地址展开成 index tile，再交给 Gather，执行端接收到的首先是一串地址。若直接提交维度描述符，规则就保留在接口里：硬件可以用递增计数器和进位逻辑产生地址，减少相应的显式索引生成、存储和读取。普通 Gather 也可以流式处理索引、在动态窗口中发现相邻请求，区别在于描述符提前提供了完整规则，减少了重新识别结构的需要。

这种信息对请求规划很有价值。设一个三维紧密正向布局，内维长度为 L₀、元素大小为 e，内维 stride 等于 e；若下一维 stride 等于 L₀e，就可在逻辑上把这两个维度折叠成更长的连续段。更外层同理，但真正发出 burst 时，仍要按对齐、页边界和接口允许的长度拆分。形状可预测还意味着可以提前知道 line 边界，以及哪些片段有机会共同覆盖同一 line。

已知 bank 映射与 stride 后，还可以分析冲突是否周期性出现，把不同的行或块交织发出，再恢复逻辑顺序。目的 Buffer 的布局也可以同时规划：搬入时采用 padding 或 swizzle，配合下一阶段计算的读取方式。源端读取连续而目的端写入集中，或者搬入很快而消费者按列读取冲突，都可能把局部优化抵消。

以上是可考虑的 ND DMA 架构能力，并不意味着某个产品已经实现了整套规划。它需要地址生成、请求调度、顺序标签、重组缓冲和同步机制；可预测地址支持预取与多个未完成请求，但仍受带宽、队列和容量限制。若所有不同 word 最终仍落到同一个 bank，仿射表达式不会改变该 bank 的服务下界。

对多维 store 还要更谨慎。不同逻辑坐标可能因 stride 设置产生别名，源和目的可能重叠，消费者可能要求确定的可见顺序。这些条件会限制交织、合并和提前写入。把结构直接交给加速器，确实提供了更多优化机会，同时也要求接口把允许的访问范围和语义表达清楚。

## 七、GPU 已经有 SIMT，为何还要 TMA

SIMT 能执行多维地址计算，也能用线程协作完成数据搬运。问题在于，这些工作会占用 SM 的指令发射、地址计算与相关寄存器资源。对于重复出现、能够由 tensor 描述符表达的大块搬运，专用机制有机会承担这部分工作，让计算线程少花精力组织数据到达。

Hopper Tuning Guide 描述的 Tensor Memory Accelerator，支持由单线程发起较大的 1–5D tensor 传输，避免数据经过寄存器中转，并减少 SM 侧的搬运指令。结合异步完成机制，可以让搬运与计算重叠，也可以采用 warp specialization，由不同线程束分别负责准备数据和消费数据。受支持的 shared memory swizzle 又能把落地布局与后续读取结合起来。[Hopper Tuning Guide][hopper]、[CUDA async copy][async]

这些收益有自己的历史边界。Ampere 的 cp.async 已有部分绕过寄存器的异步复制能力，异步搬运并非从 TMA 才开始。TMA 把多维描述、较大粒度的数据传输和相关地址处理进一步组织到专用接口中；配置与同步成本、可搬运的布局以及任务粒度，决定它是否适合某一段代码。

常见分工可以概括为 TMA 承担规则 strided/tensor 搬运，SIMT 处理更一般的离散 Gather/Scatter。它表达的是主要适用模式：SIMT 同样能处理规则访问，TMA 也受维度、shape、stride、alignment 和搬运方向限制。五六维 ND DMA 的通用设想不能直接写成 NVIDIA TMA 的产品能力，公开的常规 tensor 支持范围是 1–5D。

两者之间还有中间地带。PTX 8.6 引入了受限的二维 tensor gather4/scatter4，用于四行数据的汇集或分发，不支持 interleave 且仍受 tile 模式限制，不能据此宣称 TMA 能处理任意 scalar 索引。其架构支持也随形式不同：gather4 以 shared::cta 为目的要求 sm_100 或更高；shared::cluster 形式要求 sm_100a，PTX 8.8 起另支持 sm_100f。scatter4 则列出 sm_100a、sm_110a（原 sm_101a）及相应 family-specific target，不能一概简写为所有 sm_100+ 均支持。[PTX ISA][ptx]

从这个角度看，规则多维 tensor、块间离散而块内连续、任意元素索引，应当分成三档评估。CSA 的 KV 行选择属于需要检查中间档的场景，但是否使用 gather4、分组代价多大、能否与计算融合，都要看具体实现。专用搬运仍然需要交付地址和同步，其价值要在完整执行路径上衡量。

## 八、参数配置本身也是一次需要执行的工作

描述符保留了结构，同时把配置问题推到了前面。一个多维搬运需要表达长度、步长、起始位置和 padding 等信息；如果这些值每次都变化，执行端必须在启动前得到相应状态，地址生成器才能按正确规则工作。

用一个示意模型说明：假设每维需要五个参数，三维共有十五个参数。这里的五和十五只用于分析接口压力，不对应已核实的昇腾字段表，base 是否逐维独立也不能据此确定。再假设每参数恰好需要一条配置写入，launch 需要一条指令，那么一次完整配置与启动为十六条指令。

这时必须区分四个量。参数个数决定要表达多少信息项；指令数取决于 ISA 如何编码和传送这些信息；配置字节决定实际传输多少状态；启动延迟则由参数准备、依赖、传输及硬件接收过程共同决定。把十五次写入合成一次批量加载，可以减少显式指令数，但并不证明十五份信息能够零延迟到达。

可以考虑编译期构造静态模板、批量加载参数、通过 descriptor 指针或 ID 引用固定字段，再组合动态 base 和边界。每种方法都应说明描述符放在哪里、如何读取、何时有效，以及读它所需的带宽和延迟。对于小块频繁搬运，参数路径甚至可能先于数据路径成为瓶颈。

若配置完全不变并可安全复用 R 次，在单参数单写模型下，总指令数是 `15+R`，每次均摊 `1+15/R`。这个算例不包括数据准备、动态字段修改、同步和版本管理，也不能解释所有动态任务。分析重点应先放在如何高效形成一次操作所需的完整参数，再讨论哪些字段可以复用、怎样摊销。特别是当操作允许乱序执行时，完整参数与版本的关系必须先确定。

## 九、乱序 TMA：完整参数必须成为操作的一部分

在这里讨论的 SuperScalar NPU 设计中，TMA 是允许乱序执行的操作。由此产生的核心要求很直接：**每项操作进入可乱序执行状态前，必须绑定完整、确定的 base、stride、length、padding 参数版本；执行时不能读取被后续操作改写的公共配置。** 这是架构语义要求，以下分析尚不代表一个已经验证的实现。

考虑 A、B 两项搬运。A 先形成，但它所依赖的源数据还没有准备好；B 随后形成，依赖已经满足，可以先执行。如果系统只有一套可变公共配置，软件为 B 写入的新 base 或 stride 覆盖了 A 的值，而 A 到执行时才读取这套配置，那么 A 搬运的已经是另一组地址。即使每次 launch 只需一条指令，接口也没有正确表达这两个在飞操作。

完整状态必须与操作身份关联。所有必需参数就绪后，系统可以把它们复制到操作自己的记录中，形成快照；也可以让操作绑定一个保持有效的不可变描述符版本，稍后再读取其内容。两种方式对物理数据搬移的安排不同，但都必须保证 A 始终得到属于 A 的完整状态。仅有一个指针、却允许其指向内容被 B 原地改写，无法提供这种保证。

参数完整并不意味着操作已经可以访问内存。源数据是否就绪、目的区域是否与其他在飞写入重叠、原子或顺序约束是否满足，仍然需要依赖管理。参数依赖决定操作到底做什么，数据与顺序依赖决定什么时候允许做；把两者分开，才能保留乱序调度机会，又不破坏程序语义。

生命周期同样需要明确。参数可以分阶段构造，但在绑定之前不能把半更新状态当作可执行描述符。绑定以后，该操作看到的版本必须保持稳定；后续修改应形成新版本，或者等待合法的回收条件。描述符记录、返回缓冲和目的存储并不一定在同一时刻释放，分别需要知道谁还可能读取或写入它们。

完成通知也需要有清楚的含义。参数已经被捕获，只能说明配置可以按规定继续处理；搬运已经结束，还要结合内存一致性规则判断写入何时对消费者可见；消费者可以使用数据，也不自动意味着所有相关元数据都能立刻被复用。这些边界可以采用不同实现，但 ISA 与运行时必须能够一致解释，否则版本复用和缓冲回收会形成难以定位的竞态。

在这些条件成立后，复用仍然有价值。多个操作可以共享同一个不可变静态模板，各自绑定动态字段和版本，逻辑上形成完整状态。完整性并不要求物理上重复存储每一个常量；同时，省去重复写入也不能成为遗漏字段或依赖的理由。设计目标应当是低成本构造与交付完整参数，并允许多个版本独立在飞。

快照记录、版本表、任务标签、依赖跟踪和回收逻辑都会消耗资源。记录容量有限时需要背压，描述符缓存未命中时可能影响启动，版本管理复杂时也可能增加控制延迟。如果为了维护一套隐式公共配置而强制每次等待上一项搬运完成，又会把原本可并行的操作串行化。这些是必须进入性能和实现评估的成本，当前不能给出未经测量的面积、功耗或吞吐优势。

还应区分 NVIDIA 的异步 TMA 与这里提出的乱序执行 TMA。异步允许发起者在搬运进行时继续工作，乱序设计进一步涉及多项操作的就绪判断、执行次序、参数版本和依赖约束。公开产品的一项异步能力，不能直接证明另一种架构已经具备相同的乱序语义。

## 十、回到 Gather：把数据路径和控制路径放在一起

有些 Gather 容易优化，因为地址集合中存在足够长的连续段，布局可以调整，重复读取可以合并，或者索引模式能够反复利用，使预处理和归位成本得到摊销。还有些 Gather 持续很慢，因为请求集中在少数服务资源，索引依赖难以提前解除，复制受容量或更新成本限制，而数据本身又缺少可利用的结构。

这些差异贯穿三个层次：算法和接口表达了什么地址结构，执行端如何得到完整确定的参数，以及存储系统怎样服务最终请求。只优化其中一层，可能把压力留给下一层。源端减少了事务，目的 Buffer 仍可能冲突；搬运指令减少了，描述符生成仍可能昂贵；引入乱序以后，版本和依赖管理也可能限制并发。

所以，评价 Gather、ND DMA 或 TMA，应把索引准备、配置构造、传输、重排归位和同步都放回执行时间线，观察哪些成本能够重叠，哪些决定启动间隔和最终完成时间。本文没有运行跨平台基准，引用的手册数据、历史测量和模型例子也不构成 GPU、910B、950 与 CPU 的绝对排名。

对于 SuperScalar NPU，更实际的方向是设计一套能够保留结构、及时交付完整参数，并让多个操作安全在飞的接口。它能否带来性能收益，最终要由真实的地址分布、资源占用、配置成本和依赖执行结果回答。Gather 的优化空间，就存在于这些可表达、可规划、也可测量的条件之中。
