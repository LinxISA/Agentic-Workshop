# 从 Gather 到乱序 TMA：文章行文策划

状态：行文策划，供完整初稿审阅时参考。[正文](正文.md)已完成。资料依据见[调研笔记](参考资料/调研笔记.md)，本轮未运行基准。

## 候选标题

1. **为什么 Gather 有时很慢：从访存瓶颈到乱序 TMA**（建议）
2. 从离散地址到结构化搬运：Gather、ND DMA 与 TMA 的设计取舍
3. 一条 Gather 指令背后：存储服务能力、参数配置与乱序执行

## 总逻辑链

**不同地址仍可能合并 → 地址分布如何形成 Cache 请求 → 片上 Buffer 的 bank 服务下界 → 优化怎样改变分布并付出成本 → CSA 暴露“块间离散、块内连续” → 仿射描述符保留多维结构 → TMA 降低结构化搬运的执行开销 → 参数构造成为启动成本 → 乱序 TMA 必须绑定完整参数版本 → 以数据路径与控制路径的共同成本评价性能。**

文章从架构师视角展开，沿“为什么—机制与定量—取舍—系统成本”推进。GPU、昇腾 910B/950、SVE/SVE2 和 AVX 的差异作为机制证据穿插；主文保留关键例子，版本、接口和取证限制放在对应图注或资料注中。本文提出的 SuperScalar NPU 设计要求与公开产品事实分别标明。

## 1. 开篇：有了 Gather，为什么性能仍然差异很大

**核心问题与论点：** 从 GPU 的逐线程索引读取、NPU 的 GM/UB 接口和 CPU 向量 Gather 引出共同问题：同样描述“收集一组元素”，实际地址分布、访问层级和执行路径可能完全不同。先建立最小反例——32 个线程读取连续的 32 个 float，地址各不相同，却能有效合并；读者由此把注意力转向同一批地址能由多少存储请求共同服务。

**例子或图意：** 画连续地址、跨行连续块、随机单元素三种分布，固定有效数据量，对照其空间结构。简短说明 Gather、普通 Scatter 与 atomic scatter-add 的语义区别，重复读取与重复更新分别分析。

**证据与待查：** CUDA 合并访问、Spatter 和昇腾接口资料见笔记 §1–2、§12、§14、§20、§30。AVX2 提供 Gather，通用 Scatter 属于后续扩展范围；SVE/SVE2 与 AVX-512 的能力和吞吐须按具体指令形式核对。此处不设跨平台性能排名。

**过渡句：** 要解释这三类分布的代价，可以先沿着一次索引读取进入 Cache 的路径，看地址如何被拆成请求。

## 2. Cache 路径：有效载荷、请求服务与未完成访问

**核心问题与论点：** 沿“索引 load → 地址生成 → 数据 load”拆解依赖，再解释合并窗口与粒度、cacheline/sector 覆盖、tag 查询和 line 服务吞吐，最后接到 miss 跟踪容量、TLB/page walk 及下游排队。有效字节、独立 line/page 数与实际流量分开记账；请求量、并发能力和依赖共同决定时间。

**例子或图意：** NVIDIA CC≥6.0，限定 32 个活跃 lane、各读不同且自然对齐的 4B、基址 32B 对齐：连续或同一连续集合任意排列为 4 sectors/128B，stride 2 为 8/256B，stride 4 为 16/512B，每 lane 不同 sector 为 32/1024B；有效载荷利用率依次为 100%、50%、25%、12.5%。图上明确这是 sector 覆盖工作量，4→32 不保证慢 8 倍，也不直接等于 DRAM 事务或串行周期。

**证据与待查：** 用 CUDA/Nsight 与 MDM 支撑请求路径（§3、§8、§11），穿插 Neoverse V2 在特定 L1 命中形式下连续 LD1* 与 scaled-offset Gather 的差异，以及 Spatter 的 CPU 代际差异（§28–30）。昇腾 GM 合并案例只作为官方配置内的结果，不能外推型号；对齐建议不能当成 line 宽度。未公开的 tag 吞吐、合并窗口深度和 MSHR 数不填值；微基准需记录向量宽度、掩码、微码与缓解状态。

**过渡句：** 即使数据已经搬到片上，访问的并行度仍要经过另一层约束：同一拍有多少请求落到同一个 bank。

## 3. Buffer 路径：bank 冲突怎样变成服务时间

**核心问题与论点：** 先界定 Cache 与显式管理的 scratchpad，再说明 bank、group、subbank 和地址映射怎样决定并行服务。用 1R1W 与 2R 的区别解释读写组合：总端口名称相似，能够同时完成的请求组合仍可能不同。相同地址读取的广播/合并需按接口核实，写入及原子更新另有顺序和竞争约束。

**例子或图意：** 将同一组独立读取画成均匀分布与热点 bank 两种排队图。合并允许广播的重复 word 后，bank b 剩余 n_b 个独立读、每拍最多服务 r_b 个，理想下界为 `max_b ceil(n_b/r_b)`；注明 r_b>0、bank 可并行的模型前提，group 约束和其他竞争只会进一步限制服务。

**证据与待查：** 910B/A2/2201 的 UB bank/group 与 950PR/950DT/3510 的 subbank 资料分别使用（§9、§19–21），950 的 group 级“两读或一读一写”不能反推每 bank 物理端口。GM sector、UB 冲突和 constant memory 不同地址序列化保持区分。端口下界是分析模型，不作为未公开芯片规格。

**过渡句：** 有了这个下界，优化方案就可以逐一检查：它改变了哪一轮地址分布，又把代价移到了哪里。

## 4. 优化 Gather：改变布局、请求集合或服务能力

**核心问题与论点：** 按优化实际改变的对象展开，先讲 padding/swizzle/XOR 对布局的作用，再讲跨拍重排和分批对请求集合的作用，最后讨论重复读广播、只读复制和增加端口。每种机制同时交代容量、调度、归位、更新或物理实现成本；任意随机索引没有统一的无冲突保证。

**例子或图意：** 用 32×32→32×33 padding 串起地址映射和容量增加 3.125% 的计算，再画分批读取后恢复逻辑顺序的过程。特别注明，仅交换 lane 编号而保持同轮地址集合不变，无法降低上述模型中的 bank 集中度。CPU 的连续 load+permute、blocking、索引预取和重复写私有化可放在同一张“收益—成本”对照图中。

**证据与待查：** 官方 padding/TMA swizzle、XOR 摘要、DMM 理论和 Mergesort 特定算法结果使用各自范围（§18、§25）；Arm HISTCNT 示例与 SPC5 支撑算法重组（§27、§31）。计入逆置换、预处理、缓存污染、寄存器压力、数值顺序和副本维护。XOR 历史模拟收益、理论调度与整算法结果均不写成现代随机 Gather 的普遍加速。

**过渡句：** 真实应用经常具有部分规律，接下来用稀疏 Attention 看“离散”究竟发生在哪一层。

## 5. CSA 案例：块间离散，块内连续

**核心问题与论点：** 沿 DeepSeek CSA 的数据流讨论：压缩历史与 local window、TopK/indexer 选择、选中 KV 行或块、Attention 消费。跨 token 的选择可以离散，而单个条目沿 head 维保持连续，这种结构会同时影响合并访问、搬运粒度和计算融合。

**例子或图意：** 画“TopK 索引 → 若干连续 KV 条目 → Attention”的图，在条目间标离散、条目内标连续；并列独立 gather 中间结果与融合 kernel 直接消费两种实现组织，不预设实际采用哪一种。

**证据与待查：** 依据 DeepSeek V4 model card、DeepSelect 与 NVIDIA 实现说明（§26）。保留 CSA=Compressed Sparse Attention，其压缩后应用 DSA，HCA 为另一路。具体 kernel 是否使用受限 tensor Gather 或 SIMT/TMA 混合路径需要代码证据；仅有 Gather 语义无法推断整体性能差。

**过渡句：** 当地址中保留了连续块和可预测步长，下一步便是考虑如何把这些规律直接交给搬运硬件。

## 6. 从 index tile 到仿射 ND DMA：保留地址结构

**核心问题与论点：** 设计设想五六维、各维长度与 stride 可配置的搬运；固定任务参数后，`addr=base+Σ i_d*s_d` 是关于坐标的仿射表达式。直接交付维度描述符，可减少显式索引生成、存储和读取，并用递增计数器表达地址推进。普通 Gather 同样可以流式处理索引、在动态窗口内合并，比较时需保留这一能力。

**例子或图意：** 左侧画“仿射规则→展开 index tile→Gather”，右侧画“仿射描述符→地址生成与请求规划”。展开连续维及满足 stride 条件的相邻维折叠成 burst、预判 line 边界、预测 bank 周期、跨行块交织和逻辑顺序重组；源端读取、目的 buffer 写入与后续消费者分别标注瓶颈。

**证据与待查：** 本节机制属于设计讨论与架构推导（§35）。Padding/swizzle 落地布局、prefetch 和多个未完成请求提供优化机会，同时承担容量、调度与同步成本。结构化访问仍可能集中同 bank；store 别名、重叠与顺序限制重排。NVIDIA TMA 的公开 1–5D 支持仅作工程例，不能代表通用 6D 或证明所有设想已实现。

**过渡句：** 地址规则已经可以交付给专用机制，接着需要回答：GPU 具备 SIMT 执行能力，为什么仍为这类搬运引入 TMA。

## 7. 已有 SIMT，为何仍引入 TMA

**核心问题与论点：** 从 SM 搬运指令、地址生成和寄存器占用讲起，说明 TMA 如何以单线程发起较大 tensor 传输，结合异步计算重叠、warp specialization 和受支持的 swizzle 降低搬运组织成本。SIMT 可以执行规则访问，常见的 TMA/SIMT 分工取决于模式和成本。

**例子或图意：** 按三档排列访问：规则多维 tensor；条目内连续、条目间离散；任意元素索引。前者可评估 TMA，中间一档可评估受限 Gather 或混合路径，第三档通常需要更通用的逐元素组织；每档注明维度、shape、stride、alignment、方向和同步条件。

**证据与待查：** Hopper Tuning Guide、async copy 与 PTX 支撑 §37–38。Ampere cp.async 已有部分异步和绕寄存器能力；TMA 的二维 gather4/scatter4 有明确 target 限制，不能写成所有 TMA 均支持或绝不支持 Gather。NVIDIA 异步 TMA 与本文 SuperScalar NPU 的乱序 TMA 分别讨论，不推导相同调度语义。

**过渡句：** 搬运工作交给专用硬件后，描述一次搬运所需的参数又成为必须认真核算的前端成本。

## 8. 参数配置：一次启动之前需要完成多少工作

**核心问题与论点：** 用“三维、每维五参数、共十五参数”的示意例子说明配置压力，涉及 base、stride、length、padding 等；它是示意模型，昇腾真实字段及 base 是否逐维独立仍待查。参数个数、指令数、配置字节和启动延迟分别计量，批量加载减少指令数后，信息传输和依赖仍然存在。

**例子或图意：** 画参数准备→配置构造→绑定→launch 的时间线；比较批量配置、编译期模板、描述符指针/ID与动态字段组合。若假定单参数单写，十五写加一 launch 共十六条；同一安全且不可变配置复用 R 次为 `15+R`，均摊 `1+15/R`，注明不含数据准备、动态更新和版本管理。

**证据与待查：** 依据设计讨论和设计推导（§35–36）。这些候选方式首先必须能高效构造完整参数，复用属于后续优化；不把示意指令数转换成启动周期，也不假定所有动态任务都能共用配置。

**过渡句：** 一旦搬运操作允许乱序执行，配置的关键还包括：每项操作到底绑定了哪个完整参数版本。

## 9. SuperScalar NPU：让完整参数随乱序操作存续

**核心问题与论点：** 明确本文的核心设计要求：每项 TMA 操作进入可乱序执行状态前，必须绑定完整、确定的 base/stride/length/padding 参数版本；后续操作改写公共配置，不能改变较早操作的含义。ISA 要高效构造与交付完整状态，同时支持多在飞操作隔离及安全生命周期。

**例子或图意：** 以 A、B 两项操作示意：A 较早形成、较晚执行，B 随后配置并先执行；若 A 执行时读取 B 改写的公共配置就会出错。并列参数快照或不可变版本绑定，画出构造→参数就绪→绑定→依赖满足→执行→完成/可见→回收；源数据依赖与目的重叠检查单独标出。

**证据与待查：** 本节是本文设计要求（§36），尚未验证实现。快照、版本化、描述符实例是候选机制；固定字段可复用，但每项操作仍要得到完整有效版本。区分参数捕获、搬运结束、写入可见与消费者可用，明确更新与回收条件，避免隐式共享配置迫使任务串行。这里不声称任何 PPA 或吞吐优势。

**过渡句：** 至此，一次 Gather/TMA 的成本已经从数据地址延伸到参数构造和任务生命周期，结尾可以用同一套尺度解释哪些优化容易奏效。

## 10. 收束：结构表达、参数交付与存储服务共同决定性能

**核心问题与论点：** 回答开篇：可利用的连续性、可预测的映射、可摊销的布局或索引处理，给硬件和软件留下优化空间；随机性、热点资源、依赖以及容量/更新约束会压缩这些空间。统一评价数据路径与控制路径，避免只比较指令名字或峰值带宽。

**例子或图意：** 一张三层总图：上层是索引/仿射描述符表达，中层是完整参数构造、绑定与任务调度，下层是 Cache 请求、bank 服务和数据搬运；用 CSA、ND DMA 和乱序 TMA 标出各自改变哪一层。系统成本包含配置、索引准备、搬运、重排归位和同步，并注明它们可部分重叠，不能机械相加为总耗时。

**证据与待查：** 回指全文证据，不新增未经验证的跨平台倍数。官方案例、历史实验、手册数据、模型推导和本文设计要求分别标识；缺少可比实测时，保留机制判断和条件性结论。

**最终一段的收束方向：** Gather 的性能取决于地址中保留了多少可用结构、接口能否把完整确定的参数及时交给执行端，以及存储系统能以多大并行度服务这些请求。ND DMA 和 TMA 将结构转化为更低的地址生成与搬运开销，乱序执行进一步要求参数版本和依赖具有明确生命周期；任何优化都需要将布局、配置、调度、容量和同步成本放回同一条执行路径中核算。文章最终落在这些可检验的工程条件上，为后续实现与测量留下清晰问题。
