# U001: hybrid matrix–vector coordination across architectures

Review date: **6 October 2026**. Scope: [NPU-U-001](../talks/superscalar-npu/problem-list.md#user-described-problem-npu-u-001), including shape-dependent scheduling, local data movement, fine-grained launch/issue/synchronization overhead and low-concurrency task latency. This is a mechanism comparison, not a performance ranking. Specific vector/reduction internal efficiency belongs to U005; SRAM residency to U002; cross-card scalar/event orchestration to U006.

Evidence below combines supplied primary-source research with a read-only inspection of our timing model. No new measurements or reproduced benchmarks are supplied. Product generations and software versions are not interchangeable. Six architecture categories are covered below; matched performance evidence remains pending.

## Concise per-architecture summary

Compare dispatch, semantic work, data readiness, synchronization and memory-transfer granularity separately, including cooperation between tiles of different sizes and formats. True data dependencies cannot be removed; synchronization broader than the actual dependency, or waiting for an entire block when only part is needed, may introduce additional waiting. No fixed tile size is assumed optimal.

### Our superscalar NPU

- **Mechanism:** Bounded readiness selection, logical tags, conditional partial-cell readiness and bank/resource checks coordinate tile producers and consumers; see [current model evidence](#our-superscalar-npu-current-model-evidence).
- **Responsibility:** Software supplies tile/layout and dependency semantics; the hardware model manages eligible readiness, binding, issue and backpressure. It does not implement unrestricted global out-of-order execution.
- **Fit / cost:** Potentially avoids unnecessary whole-tile waiting when independent or partially ready work exists. Scoreboards/tags, selection, arbitration, recovery and liveness are costs; shape support is conditional and no quantitative win is established.

### NVIDIA Hopper

- **Mechanism:** Fused tiled Attention combines Tensor Core matrix work with non-matrix work through WGMMA, TMA, producer/consumer warp specialization and asynchronous barriers. Warp scheduling, warpgroup matrix work and DMA are separate granularities. [Hopper guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/), [FlashAttention-3](https://arxiv.org/html/2407.08608v2).
- **Responsibility:** Compiler/kernel software selects tiling, layouts, multibuffering, software pipelines and synchronization; runtime and hardware schedule eligible work and execute asynchronous operations. [Hopper guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/).
- **Fit / cost:** Independent tile activities can overlap while single-tile dependencies remain. Registers/SMEM, barriers, occupancy and startup/drain costs constrain benefit; low-concurrency gains need a matched case. [FlashAttention-3](https://arxiv.org/html/2407.08608v2).

### Ascend 910B / Atlas A2

- **Mechanism:** Explicit Cube/Vector pipelines coordinate independent AIC/AIV control, staged buffers and events; A2 examples use GM-addressed exchange, which can hit L2. Paths differ by generation. [Work modes](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_10_0008.html), [primary paper](https://arxiv.org/html/2505.15112v1#S3).
- **Responsibility:** Host tiling and kernels select work partitions, layouts and buffers; asynchronous APIs, queues/events and hardware execution coordinate stages. [Host tiling](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/opdevg/Ascendcopdevg/atlas_ascendc_10_00021.html), [async programming](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/850/opdevg/Ascendcopdevg/atlas_ascendc_10_10015.html).
- **Fit / cost:** Incremental consumption and interleaved rounds can exploit overlap in specified cases; UB/L1/L0 capacity, exchange traffic and synchronization matter. The long-sequence backward example does not prove decode performance; newer 3510 paths must be treated separately. [A2 example](https://www.hiascend.com/developer/techArticles/20240607-1), [3510 specification](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/programug/Ascendcopdevg/docs/en/guide/programming_guide/advanced_programming/hardware_implementation/architecture_spec/npu_architecture_version_3510.md).

### TPU / Pallas

- **Mechanism:** Compiler-scheduled asynchronous engines combine tiled matrix/vector work with DMA, buffers and semaphores. DMA/compute overlap is not automatically complete MXU/softmax overlap. [Pipelining](https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html), [FA implementation](https://github.com/jax-ml/jax/blob/main/jax/experimental/pallas/ops/tpu/flash_attention.py).
- **Responsibility:** Compiler and kernel define fusion, layouts, tile schedules and synchronization; hardware executes asynchronous engines, with supported runtime indexing where applicable. [Details](https://docs.jax.dev/en/latest/pallas/tpu/details.html), [runtime indexing](https://docs.jax.dev/en/latest/pallas/tpu/sparse.html).
- **Fit / cost:** Stable shapes and effective schedules can use overlap well; VMEM footprint, layout/reduction axes and pipeline startup/drain affect short-task latency. Products/generations and matched performance remain separate questions. [Matmul tutorial](https://docs.jax.dev/en/latest/pallas/tpu/matmul.html).

### Tenstorrent

- **Mechanism:** Software-orchestrated, readiness-synchronized dataflow uses L1 circular-buffer reserve/wait/push/pop and unpack/math/pack ownership. FPU/SFPU overlap depends on kernel/configuration and shape. [Metalium guide](https://github.com/tenstorrent/tt-metal/blob/main/METALIUM_GUIDE.md), [compute engines](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/advanced_topics/compute_engines_and_dataflow_within_tensix.html).
- **Responsibility:** Kernels place and partition work; RISC-V roles command compute/NoC engines, while runtime readiness and buffer flow control coordinate producers and consumers. Static placement is not a fixed cycle schedule. [Metalium guide](https://github.com/tenstorrent/tt-metal/blob/main/METALIUM_GUIDE.md).
- **Fit / cost:** Streaming and buffering can overlap eligible activity; L1/Dst capacity, ownership, command sequencing and chunk geometry constrain it. Historical reports and an implementation investigation are not universal performance verdicts. [FA report](https://github.com/tenstorrent/tt-metal/blob/main/tech_reports/FlashAttention/FlashAttention.md), [investigation](https://github.com/tenstorrent/tt-metal/issues/55759).

### Groq published TSP

- **Mechanism:** Compiler-timed deterministic streaming connects matrix/vector/memory/switch slices; chaining can avoid intermediate writeback. [ISCA 2020](https://www.groq.com/wp-content/uploads/2020/06/ISCA-TSP.pdf).
- **Responsibility:** The compiler arranges instructions and data in space/time; runtime synchronization and deskew preserve the network timing contract. These are published designs, not claims about every current product. [ISCA 2022](https://groq.com/wp-content/uploads/2023/05/GroqISCAPaper2022_ASoftwareDefinedTensorStreamingMultiprocessorForLargeScaleMachineLearning-1.pdf).
- **Fit / cost:** Predictable schedules can exploit streaming and chaining; placement, timing contracts, layout and enough independent work are required. True Attention dependencies and insufficient overlap can still create bubbles; matched latency/energy evidence remains pending. [ISCA 2020](https://www.groq.com/wp-content/uploads/2020/06/ISCA-TSP.pdf), [ISCA 2022](https://groq.com/wp-content/uploads/2023/05/GroqISCAPaper2022_ASoftwareDefinedTensorStreamingMultiprocessorForLargeScaleMachineLearning-1.pdf).

**Responsibility takeaway:** Compilers/kernels perform tiling, layout, fusion, multibuffering, software pipelining and synchronization. Stable shapes and latencies can support efficient schedules; runtime differences are handled through each platform's execution and flow-control mechanisms. Compare how responsibilities are divided, and their whole-core costs, rather than assuming either software or dynamic hardware removes dependencies or universally wins.

## Our superscalar NPU: current model evidence

Version scope: handwritten C++ TimingSim on `feat_pyc_model`, commit `d5419b3e721df47daae02c38ef2a9b82187e5149`. This is timing-model implementation evidence, not a claim of synthesized RTL, physical PPA or a complete PyCircuit core. Detailed local source mappings remain local.

- **Responsibility:** Software supplies operation decomposition, tile geometry, layout and dependency semantics. The model performs readiness checks, bounded queue selection, resource binding/arbitration and backpressure handling. Automatic compiler selection of optimal shape-dependent decompositions or schedules has not been established by this inspection.
- **Matrix–vector handoff:** Conditional cell-level readiness allows eligible vector consumers to begin on available portions of a producer's tile instead of waiting for whole-tile completion. Other consumers can retain whole-tile readiness. Cell readiness is tracked by logical identity and offset; producer eligibility, configuration and shape alignment constrain applicability.
- **Scheduling and locality:** CUBE scans a bounded queue subject to dependency, chain-order, speculation and execution/storage-resource gates. VEC issues DATA_READY work by execution class, with destination-buffer capacity, resource initiation intervals and shared-queue backpressure checks. Optional ready bypass is not unrestricted global out-of-order execution: the cell-mode vector block entrance retains an ordering constraint.
- **Buffers and synchronization:** Logical tags/generations can be separated from physical binding; binding failure causes waiting. Shared local storage arbitrates per-bank requests under requester port budgets. Some CUBE/VEC paths coordinate bank reservations. Static and dynamic paths coexist; configuration matters, and a default flag alone neither disproves a mechanism nor proves its use in a particular run.
- **Conditions / costs / unknowns:** Queue/state/tag bookkeeping, selection, arbitration, buffering and recovery consume resources. Cell geometry has documented alignment restrictions; arbitrary independent source shapes or nonlinear strides are not established. No matched Attention shape sweep, low-concurrency end-to-end profile, automatic retuning result or physical cost comparison was verified. These mechanisms create overlap opportunities but do not eliminate true dependencies or prove an advantage.

## NVIDIA GPGPU

**Hopper scope.** Kernel software manages tiled QK → softmax → PV decomposition, buffering and producer/consumer warp specialization. Tensor Cores perform matrix work; CUDA/SFU paths handle relevant non-matrix work. TMA and asynchronous WGMMA enable software pipelines that overlap independent tile activities. A single tile's true QK-to-softmax-to-PV dependencies remain. See the [Hopper tuning guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/) and [FlashAttention-3 paper, v2](https://arxiv.org/html/2407.08608v2).

**Blackwell SM100 scope.** `tcgen05` MMA can be issued by a single thread, with Tensor Memory accumulators; this changes control and accumulator placement rather than removing kernel scheduling responsibility. [CUTLASS 4.5.2 tcgen05 documentation](https://docs.nvidia.com/cutlass/4.5.2/media/docs/pythonDSL/mma_docs/tcgen05_programming.html). FlashAttention-4 describes TMEM, different warpgroups and software pipelining; it is a specific implementation, not proof of automatic optimization for all shapes. [FlashAttention-4, v1](https://arxiv.org/html/2603.05451v1). Blackwell Ultra SFU enhancements must not be attributed indiscriminately to B200. [Blackwell Ultra architecture article](https://developer.nvidia.com/blog/inside-nvidia-blackwell-ultra-the-chip-powering-the-ai-factory-era/).

**Shapes and low concurrency.** Runtime shape selection within TensorRT optimization profiles does not require a fresh compilation for every shape. [TensorRT dynamic-shape documentation](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/dynamic-shapes-basics.html). TensorRT-LLM attention can use heuristic multi-block execution when batch × heads is small, with its own partitioning and coordination tradeoffs; this is not a universal decode benefit. [TensorRT-LLM attention documentation](https://nvidia.github.io/TensorRT-LLM/features/attention.html).

**Conditions / costs / unknowns.** Independent work, occupancy and adequate buffers are necessary for useful overlap. Registers, shared memory, barriers, producer/consumer control and extra partitioning must be included in the matched resource/latency ledger. The cited kernels and runtime mechanisms do not establish a result for our chosen workload or baseline. [Hopper tuning guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/), [FlashAttention-3](https://arxiv.org/html/2407.08608v2), [TensorRT-LLM attention](https://nvidia.github.io/TensorRT-LLM/features/attention.html).

## Ascend NPU

**910B / Atlas A2 example.** Cube AIC and Vector AIV have independent control; Cube uses L1/L0 storage and Vector uses UB. GM-addressed interchange may hit L2, so it must not be described as necessarily travelling to HBM on every exchange. See [official work modes](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_10_0008.html) and the [primary paper, section 3](https://arxiv.org/html/2505.15112v1#S3).

**Responsibility and overlap.** Host tiling and kernel software choose partitioning and buffers. TPipe/TQue, DoubleBuffer and asynchronous execution expose DMA/compute overlap and coordination; cross-AIC/AIV events handle relevant synchronization. Queue depth is not the same quantity as allocated buffer count. [Host tiling](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/opdevg/Ascendcopdevg/atlas_ascendc_10_00021.html), [asynchronous programming](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/850/opdevg/Ascendcopdevg/atlas_ascendc_10_10015.html).

The official A2 FlashAttention backward example caches multiple Matmul tiles in GM, uses asynchronous `IterateAll`, and incrementally consumes results with Vector work while interleaving the next round. Its evidence concerns a specified long-sequence backward case; it does not establish decode or short-task performance. [Official example](https://www.hiascend.com/developer/techArticles/20240607-1).

**Conditions / costs / generation boundary.** Partitioning, staging storage, exchange traffic, synchronization and startup/drain costs need workload-specific evaluation. DoubleBuffer may be unhelpful when the Vector work already fits a single invocation. [DoubleBuffer best practice](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_best_practices_10_0033.html). Newer architecture 3510 documents L0C → UB, UB ↔ L1 and SSBuffer scalar messaging; do not generalize the A2 GM-exchange path to every generation. [3510 architecture specification](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/programug/Ascendcopdevg/docs/en/guide/programming_guide/advanced_programming/hardware_implementation/architecture_spec/npu_architecture_version_3510.md). Matched low-concurrency latency and the best tiling choice for the target shapes remain unknown here.

## TPU / compiler-directed execution

**Responsibility and handoff.** Compiler/kernel scheduling manages asynchronous MXU, VPU and scalar activities. Pallas can express fusion, DMA, buffers and semaphores. [TPU pipelining documentation](https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html). The official FlashAttention implementation expresses tiled QK, max/exp/sum, PV and running state. [JAX source](https://github.com/jax-ml/jax/blob/main/jax/experimental/pallas/ops/tpu/flash_attention.py) (moving main reference; pin a revision before code-based slide claims).

**Conditions and shape handling.** DMA/compute overlap does not prove complete MXU/softmax overlap: independent work, sufficient buffers and an effective schedule are still necessary. [Pipelining](https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html). Layout and reduction axes affect execution cost; VMEM tiling and pipeline startup/drain matter for short tasks. [TPU details](https://docs.jax.dev/en/latest/pallas/tpu/details.html), [matmul tutorial](https://docs.jax.dev/en/latest/pallas/tpu/matmul.html). Bounded runtime indexing provides some dynamic behavior; shape variation should not be described as universally requiring recompilation. [Sparse computation documentation](https://docs.jax.dev/en/latest/pallas/tpu/sparse.html).

**Generation boundary.** v4 has two TensorCores with four MXUs each; v5e has one TensorCore with four MXUs; v5p has two TensorCores with four MXUs each; v6e has one TensorCore with two larger 256 × 256 MXUs versus older 128 × 128 arrays. Unit count alone is not a performance comparison. [v4](https://docs.cloud.google.com/tpu/docs/v4), [v5e](https://docs.cloud.google.com/tpu/docs/v5e), [v5p](https://docs.cloud.google.com/tpu/docs/v5p), [v6e](https://docs.cloud.google.com/tpu/docs/v6e).

**Costs / unknowns.** Buffer footprint, layout/data movement, semaphore coordination and compilation/scheduling choices must be assessed alongside useful overlap. No common-shape performance or low-concurrency winner is established by these references. [Pipelining](https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html), [matmul](https://docs.jax.dev/en/latest/pallas/tpu/matmul.html).

## Tenstorrent / software-orchestrated, readiness-synchronized dataflow

**Responsibility and handoff.** Tensix RISC-V reader/writer and unpack/math/pack roles issue commands to NoC, FPU, SFPU and other engines; this does not mean the RISC-V CPUs themselves perform tensor arithmetic. L1 circular-buffer reserve/wait/push/pop operations establish producer/consumer ownership and backpressure. Static placement is not necessarily a cycle-by-cycle schedule. [Metalium guide](https://github.com/tenstorrent/tt-metal/blob/main/METALIUM_GUIDE.md) (moving main reference; pin a revision before slide code claims).

**Local coordination.** FPU and SFPU share Dst storage, with unpack/math/pack ownership and synchronization affecting handoff and possible overlap. [Tensix compute engines and dataflow](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/advanced_topics/compute_engines_and_dataflow_within_tensix.html).

**Attention evidence boundary.** The historical Wormhole FlashAttention report describes QKV double buffering, L1 running statistics, causal load balancing and chunk choices; it listed matmul/softmax overlap as future work at that time. This is not evidence that current implementations cannot overlap them. [Historical report](https://github.com/tenstorrent/tt-metal/blob/main/tech_reports/FlashAttention/FlashAttention.md). A September 2026 official-repository investigation distinguishes non-streaming FP32 Dst execution, where FPU subtraction and SFPU exp share the math thread and serialize, from a streaming path where the pack thread issues exp with shape-dependent overlap. Treat this as an implementation investigation, not general hardware performance evidence. [Issue 55759](https://github.com/tenstorrent/tt-metal/issues/55759).

**Conditions / costs / unknowns.** L1 buffers, Dst ownership, command-thread coordination, chunk geometry and independent work govern useful overlap. Host asynchronous dispatch or trace replay alone does not demonstrate FPU/SFPU overlap. Neither a historical report nor the issue establishes matched low-concurrency latency or a winner against other architectures. [Compute-engine documentation](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/advanced_topics/compute_engines_and_dataflow_within_tensix.html), [implementation investigation](https://github.com/tenstorrent/tt-metal/issues/55759).

## Groq / published compiler-timed deterministic streaming

**Published TSP design scope.** Matrix, vector, memory and switch slices exchange streams. The ISA exposes latency and arrival timing; the compiler arranges instructions and data in space and time, including delays. Slice chaining can avoid intermediate writeback. These statements concern the published architecture, not every current Groq product. [ISCA 2020 original paper](https://www.groq.com/wp-content/uploads/2020/06/ISCA-TSP.pdf).

**Synchronization and responsibility.** The published multi-TSP network seeks to avoid dynamic arbitration and conventional buffered flow control, while runtime synchronization and deskew maintain the timing contract. Deterministic scheduling therefore does not mean absence of runtime synchronization. [ISCA 2022 original paper](https://groq.com/wp-content/uploads/2023/05/GroqISCAPaper2022_ASoftwareDefinedTensorStreamingMultiprocessorForLargeScaleMachineLearning-1.pdf).

**Conditions / costs / unknowns.** Timing contracts, spatial placement, layouts and sufficient independent work must fit the execution schedule. Neither streaming nor compiler timing removes the true QK → softmax → PV dependency; insufficient independent tiles or staging can leave bubbles. The cited design papers do not establish an optimal schedule, current product behavior or matched Attention/short-task performance. [ISCA 2020](https://www.groq.com/wp-content/uploads/2020/06/ISCA-TSP.pdf), [ISCA 2022](https://groq.com/wp-content/uploads/2023/05/GroqISCAPaper2022_ASoftwareDefinedTensorStreamingMultiprocessorForLargeScaleMachineLearning-1.pdf).

## Granularity and asynchronous programming responsibility

Compare **dispatch granularity, semantic work granularity, data-readiness granularity, synchronization granularity and memory-transfer granularity separately**. A tile-level operation may expose cell-level readiness while retaining block-order constraints; neither label alone describes the whole scheduling policy.

- **NVIDIA:** Ready-warp selection is not equivalent to CPU out-of-order instruction scheduling. Hopper warpgroup WGMMA and TMA cooperation introduce distinct matrix-operation and transfer/control granularities; inspect the actual kernel rather than treating every operation as one warp. [Hopper guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/), [FlashAttention-3](https://arxiv.org/html/2407.08608v2). Whether warp granularity is too fine for this workload is a user hypothesis requiring evidence, not a conclusion.
- **Ascend:** Distinguish host/kernel tile work, Cube/Vector execution, exchange buffers, events and DMA transfers. A possible related source is a specific FA/FAG operator optimization: UB is partitioned among inputs, outputs, intermediates and double buffers, with a largest individual allocation of 32 KB corresponding to an 8 × 1024 FP32 Vector base tile. This is an operator buffer/tile choice, not a fixed hardware asynchronous or out-of-order scheduling granularity; whether the user meant this example remains unconfirmed. [Pinned FA/FAG design document](https://gitee.com/ascend/cann-ops-adv/blob/186db5bf93202bea2bde82795165098fa62ce84a/docs/common/FA-FAG%E7%AE%97%E5%AD%90%E8%AE%BE%E8%AE%A1%E4%BB%8B%E7%BB%8D.md). Matmul `SetFixSplit` configures `baseM`/`baseN` in elements subject to local-memory and alignment constraints, further distinguishing operator tiling from hardware issue granularity. [SetFixSplit API](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/850/API/ascendcopapi/atlasascendc_api_07_0681.html). [Host tiling](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/opdevg/Ascendcopdevg/atlas_ascendc_10_00021.html), [asynchronous programming](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/850/opdevg/Ascendcopdevg/atlas_ascendc_10_10015.html).
- **TPU:** Separate Pallas block/tile work, MXU/VPU execution, DMA buffering and semaphore synchronization; a compiler-directed program can still contain asynchronous operations and runtime indexing. [Pipelining](https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html), [sparse computation](https://docs.jax.dev/en/latest/pallas/tpu/sparse.html).
- **Our model:** Tile semantics plus conditional cell readiness can reduce whole-tile waiting for eligible consumers. Bounded queues, logical tags and resource-aware issue may let hardware-managed readiness replace some software coordination, but a reduction in software synchronization burden is a hypothesis, not an observed result. Dependencies, producer eligibility, ordering constraints and explicit program semantics remain necessary. Scoreboards/tags, arbitration, recovery and forward-progress obligations are costs, not incidental details. No profile or PPA proof is supplied.

For every architecture, ask who owns asynchronous operation and buffer lifetimes, completion events, producer/consumer dependencies and synchronization placement. Compare programming/debugging complexity and required invariants as well as overlap opportunity; finer granularity is not intrinsically better.

## Common comparison ledger

Compare the same workload decomposition, shape, precision, numerical requirements, resource budget and architectural level. Record compiler/kernel/runtime/hardware responsibilities separately, then examine matrix–vector handoff, buffering/locality, asynchronous synchronization and startup/drain behavior.

Measure throughput, task latency, utilization, storage, bandwidth, control cost and energy as applicable, with correctness and liveness requirements. Whole-core area, power and clock timing include scheduling state, tags, comparisons, arbitration and recovery. Label source-supported mechanisms, author assumptions and pending measurements separately. None of these architectures is assumed to lack a solution; our superscalar approach must satisfy the same evidence and cost standard.

## Remaining evidence gaps

The exact meaning of the spoken “32 KD” remains unresolved despite a possible operator-level 32 KB source; hardware granularity must be specified by operation and platform. Matched profiles, shape sweeps, low-concurrency latency and whole-core physical cost remain pending across all six categories; no ranking is established.
