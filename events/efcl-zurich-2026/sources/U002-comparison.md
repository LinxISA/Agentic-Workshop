# U002: latency hiding and physical storage residency

Review date: 6 October 2026. Scope: [NPU-U-002](../talks/superscalar-npu/problem-list.md#user-described-problem-npu-u-002). Five-category mechanism comparison; no area ranking or quantitative benefit is established. This is preparation evidence, separate from the U001 review PR.

## Shared question and accounting layers

Separate **request metadata/tracking**, **destination/returned-data buffering**, and **compute-live payload**. In-flight byte count does not establish issue-time SRAM reservation. Allocation lifetime is not value lifetime: a preallocated pool can serve successive values, while completion and ownership release are distinct events. Increased capacity alone does not imply increased latency; additional buffering cannot remove a bandwidth bottleneck.

Ask for each platform: who allocates capacity, when a value acquires ownership, where returns wait, what marks ready, when reuse is safe, and how admission/backpressure preserves forward progress. Compiler lifetime planning and runtime/hardware management are both relevant approaches.

## Reviewed five-architecture summary

The common question is how to hide latency without retaining unnecessary physical payload capacity. Keep request metadata, returned-data buffers, allocated pools and genuinely live compute values separate; completion does not automatically release ownership, and slot reuse does not free the enclosing pool.

**Review conclusion:** Compiler-orchestrated storage need not reserve for worst-case latency: lifetime analysis, streaming and sliced prefetch can reduce conservatism, while runtime completion/backpressure handles variation. More slack/buffers can trade capacity for robustness, or the pipeline can stall. Conditional late binding is another responsibility split, not removal of return storage or the peak true live set. None of the five is assigned a numerical storage, software-complexity or PPA advantage.

## Our superscalar NPU: inspected timing-model scope

Version scope: TimingSim `feat_pyc_model`, HEAD `d5419b3e721df47daae02c38ef2a9b82187e5149`; no claim of complete RTL or physical cost. Private source navigation remains local.

- **Mechanism / responsibility:** Logical Tile identity includes virtual tag/generation independently of a physical address. The model manages mapping, physical binding, resource admission and backpressure; software still supplies operation geometry, reuse and dependencies.
- **Allocation / release:** Virtual allocation can precede physical binding. Ordinary issue-time binding coexists with a conditional real-L2 local-load path that requests binding after returned-data-ready. Shared staging follows a different path. Binding failure waits for capacity. Early release checks consumers, the non-flush boundary, aliases and physical references; it is not unconditional release after one read.
- **Layers / backpressure:** Inflight request metadata and returned-data machinery remain present while local Tile binding waits. Bind-request/grant queues and allocation arbitration are bounded. Cell readiness can support partial consumption but does not establish cell-by-cell allocation or release.
- **Fit / costs / unknowns:** Potentially reduce avoidable physical destination residency while retaining logical dependencies. Mapping/generation state, return buffering, binding arbitration, alias tracking and recovery still cost resources. Required live data and completion capacity remain necessary; late allocation alone guarantees neither reduced minimum capacity nor liveness. Matched occupancy/lifetime and throughput/energy evidence is pending.

## NVIDIA Hopper

- **Mechanism / responsibility:** Resident warp register contexts and CTA shared-memory allocations constrain occupancy. Software selects pipeline staging and lifetimes; hardware tracks dependencies and applies queue/resource backpressure. Internal MSHR/response-buffer allocation policy is not publicly specified by these sources. [Hardware multithreading](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html#hardware-multithreading).
- **Allocation / release:** TMA pipelines use software-allocated shared-memory stages: producer waits for empty → copies → consumer waits for full → computes → releases. Copy completion is not consumer completion. TMA avoiding intermediate registers is not proof of late SRAM binding. [CUTLASS Hopper warp specialization](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/efficient_gemm.html#hopper-warp-specialization), [async copies](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html).
- **Backpressure / fit / cost:** More stages may increase overlap while consuming CTA memory and affecting occupancy. Register ownership is not universally fixed: `setmaxnreg` can redistribute registers within a CTA pool. These mechanisms do not establish a hardware late-binding policy for every payload or a matched U002 performance advantage. [CUTLASS](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/efficient_gemm.html#hopper-warp-specialization), [setmaxnreg](https://docs.nvidia.com/cuda/parallel-thread-execution/#miscellaneous-instructions-setmaxnreg).

## TPU / Pallas and compiler lifetime planning

- **Mechanism / responsibility:** Pallas DMA pipelines use VMEM slots and configurable multibuffering, with two buffers as the documented default; lookahead prefetch requires an available slot. This is explicit compiler/kernel scheduling and buffer ownership, not evidence of unbounded request or payload capacity. [Pipelining](https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html).
- **Allocation / release:** DMA destination-write and source-read completion can be distinct. Completion must be distinguished from subsequent ownership/reuse. Distributed capacity semaphores prevent overwrite; bounded run-ahead tolerates some timing variation. [Async copy API](https://docs.jax.dev/en/latest/_autosummary/jax.experimental.pallas.tpu.make_async_copy.html), [run-ahead and races](https://docs.jax.dev/en/latest/pallas/tpu/distributed.html#run-ahead-and-race-conditions).
- **Fit / cost / unknowns:** More slots consume VMEM and can hide latency only with appropriate schedules and bandwidth. OpenXLA memory-space assignment provides lifetime, eviction/prefetch and sliced-copy planning that can delay destination allocation: a compiler approach to residency optimization, not hardware late binding or proof that a particular Pallas pipeline uses it by default. [Allocation definitions](https://github.com/openxla/xla/blob/main/xla/service/memory_space_assignment/allocation.h), [memory-space assignment](https://github.com/openxla/xla/blob/main/xla/service/memory_space_assignment/memory_space_assignment.h). These moving references require revision pinning before code-based slides; internal request/return-buffer policy and matched gains remain unspecified here.

## Ascend — TPipe/TQue buffer ownership

- **Mechanism / responsibility:** Kernel/API buffer planning establishes a TPipe-managed physical pool via `InitBuffer`; tensor allocation and queue operations manage ownership within that pool. [InitBuffer](https://www.hiascend.com/doc_center/source/en/canncommercial/850/API/ascendcopapi/atlasascendc_api_07_0110.html).
- **Allocation / release:** `FreeTensor` returns a tensor buffer to the pool; it does not establish that the physical pool itself is freed or allocated only when data returns. The pool lasts until the appropriate TPipe destruction/reset lifecycle. [FreeTensor](https://www.hiascend.com/doc_center/source/en/canncommercial/850/API/ascendcopapi/atlasascendc_api_07_0139.html).
- **Backpressure / fit / cost:** Queue depth is not DoubleBuffer count. Buffer multiplicity can enable overlap but consumes local capacity; queue/events and ownership must prevent reuse before consumption finishes. Internal request metadata/return-buffer policies and generation-specific quantitative costs are not established by these API descriptions. [TQue](https://www.hiascend.com/doc_center/source/en/canncommercial/850/API/ascendcopapi/atlasascendc_api_07_0137.html). Platform-specific internals and matched evidence remain unspecified here.

## Tenstorrent — L1 circular-buffer ownership

- **Mechanism / responsibility:** Host `CreateCircularBuffer` allocates L1 address-space capacity; kernels coordinate producer/consumer ownership of that capacity. This separates physical buffer allocation from the lifetime of individual values. [Circular buffers](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/apis/host_apis/buffers/CircularBuffers.html).
- **Allocation / release:** `reserve_back` waits for free space without advancing the pointer; push publishes produced data and pop reclaims consumed capacity. Finishing a write does not automatically publish, and finishing a read does not automatically free. [reserve_back](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/apis/kernel_apis/circular_buffers/cb_reserve_back.html), [Metalium guide](https://github.com/tenstorrent/tt-metal/blob/main/METALIUM_GUIDE.md).
- **Backpressure / fit / cost:** Circular-buffer flow control supports streaming and bounded producer run-ahead; L1 capacity, ownership discipline and NoC/engine throughput constrain overlap. This is pool/slot reuse, not evidence of physical allocation at response arrival. Internal request/return buffering and matched residency savings remain unknown here; matched lifetime/cost evidence remains unspecified here. [Metalium guide](https://github.com/tenstorrent/tt-metal/blob/main/METALIUM_GUIDE.md).

## Variable latency and compiler-orchestrated storage

**Conditional mechanism hypothesis:** When memory latency varies, a compiler/kernel may provision conservative lifetimes, multibuffering or lookahead relative to assumed/profiled timing. This is not a claim that every compiler reserves for worst-case latency or overallocates SRAM. Separate correctness resource guarantees (no overwrite, valid ownership, sufficient completion capacity) from performance latency slack intended to keep a pipeline busy.

Static live-range planning can coexist with runtime DMA completion, semaphores, backpressure and stalls. A late transfer can extend slot occupancy or delay a stage; additional buffers may improve tolerance while consuming capacity, and do not solve inadequate bandwidth. [Pallas pipelining](https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html), [distributed run-ahead](https://docs.jax.dev/en/latest/pallas/tpu/distributed.html#run-ahead-and-race-conditions).

Compiler lifetime analysis, eviction/prefetch planning, sliced copies and streaming reuse can reduce conservatism rather than reserving every payload early. This is a valid alternative to hardware-managed binding; particular defaults and outcomes require a pinned compilation. [XLA allocation planning](https://github.com/openxla/xla/blob/main/xla/service/memory_space_assignment/allocation.h), [memory-space assignment](https://github.com/openxla/xla/blob/main/xla/service/memory_space_assignment/memory_space_assignment.h).

Our model's conditional late binding defers part of destination reservation, while still requiring request/return buffering, admission and forward-progress management. It cannot remove the peak genuinely live working set. Compare whether storage/waiting moves elsewhere before claiming savings; no additional SRAM percentage is inferred.

## Control and resource overheads

This is a functional responsibility inventory, not PPA or a complexity ranking. **Fixed pool** allocation, **per-request/value state**, **synchronization operations** and **runtime waiting** are different costs. A reusable slot does not imply release of its enclosing CTA allocation, VMEM/UB/L1 pool or global storage.

| Architecture | Allocation/tracking and movement control | Synchronization, software work and waiting |
| --- | --- | --- |
| Our timing model | Virtual-tag/generation mappings, physical binding/free references, alias and consumer state; inflight/return buffers, bounded bind admission and local-memory arbitration. | Readiness/completion and recovery controls enforce some operand coordination below the API. Software still supplies geometry, reuse and program semantics; capacity waits and liveness remain obligations. No proven reduction in total programming complexity. |
| NVIDIA Hopper | Resident registers and CTA SMEM pools; per-operation dependency tracking and TMA/load-store control. Internal request/response allocation detail is not publicly specified. | Warp specialization assigns producer/consumer roles; barriers manage stage ownership/completion. TMA handles transfers, while setmaxnreg redistributes CTA registers: these are separate mechanisms. Compiler/kernel buffer schedules and lifecycle code remain; stage/occupancy waits are costs. |
| TPU / Pallas | VMEM slots, DMA request/control and compiler live-range/eviction/prefetch planning; internal request/return structures are unspecified here. | Semaphore/completion operations and compiler/kernel buffer schedules manage ownership and run-ahead. Extra slack/buffers trade space for tolerance; late transfers can stall. Lifetime/sliced-prefetch optimization can reduce conservatism. |
| Ascend | TPipe-managed local pools, tensor allocation/free within pools, queue state and DMA/pipe control; per-request return structures are unspecified here. | Kernel queue/event lifecycle, SetFlag/WaitFlag and cross-core coordination; FreeTensor is pool-slot reuse, not pool destruction. Full queues, dependencies and transfer delays cause waiting. |
| Tenstorrent | Host-allocated L1 circular buffers, producer/consumer slot bookkeeping and NoC commands/counters; command-slot reuse and payload completion have different lifetimes. | Kernels reserve/wait/push/pop, use transfer barriers and semaphores, and preserve buffer ownership. CB capacity and engine/NoC throughput can stall; a generic NoC late allocator is not inferred. |

## Common tradeoff

Compare tracking capacity, return-buffer occupancy, allocated pool size, per-value ownership interval and required live compute data separately. Check admission/credits, fairness, backpressure and recovery against [U008 forward progress](../talks/superscalar-npu/problem-list.md#user-described-problem-npu-u-008). Apply the same throughput, task-latency, storage, bandwidth, control-cost and energy criteria to all designs; a shorter destination interval is not a complete system benefit if waiting or storage merely moves elsewhere. No default flag, historical bug or universal superiority claim is used here.

## Programming and flow-control follow-up

[Actual programming examples](U002-programming-examples.md) distinguish high-level dependency expression, verification-wrapper waits and lower-level operation emission.

On Wormhole B0, a NoC command slot can become reusable after first-hop acceptance, while a read completes after data is written into L1; metadata-slot and payload-slot lifetimes differ. Cut-through routing does not imply a full payload allocation at every hop. [Counters](https://github.com/tenstorrent/tt-isa-documentation/blob/main/WormholeB0/NoC/Counters.md), [routing paths](https://github.com/tenstorrent/tt-isa-documentation/blob/main/WormholeB0/NoC/RoutingPaths.md). Kernel ownership follows reserve → async read → read barrier → push, then wait → consume → pop. Circular-buffer capacity can block the producer; do not infer a general NoC credit-based late allocator from these APIs. [Metalium guide](https://github.com/tenstorrent/tt-metal/blob/main/METALIUM_GUIDE.md).

Ascend DeQue returns a tensor address/ownership reference rather than copying its payload; queue depth remains distinct from buffer count. Explicit SetFlag/WaitFlag coordinates pipe dependencies. [TQue](https://www.hiascend.com/doc_center/source/en/canncommercial/850/API/ascendcopapi/atlasascendc_api_07_0137.html), [SetFlag/WaitFlag](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/81RC1beta1/API/ascendcopapi/atlasascendc_api_07_0177.html).

The [pinned FA3 producer/consumer example](U002-programming-examples.md#actual-gpu-counterpart-flashattention-3-hopper) exposes stage acquire, transaction completion and consumer release separately. The actual Tile benchmark example expresses operand dependencies at a higher layer and retains explicit wrapper waits; matching lower-layer evidence is necessary before judging total control burden.
