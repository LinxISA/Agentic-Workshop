# U003: mixed-precision representation and instruction preparation

Read-only review: 6 October 2026. Scope: [NPU-U-003](../talks/superscalar-npu/problem-list.md#user-described-problem-npu-u-003). The spoken “IP32/8/4” does not identify FP versus INT; retain both possibilities. Representative paths for our model/PTO, GPU, Ascend, TPU, Tenstorrent, x86 and Arm are included; exact deployment and matched-performance evidence remain limited. No tests or benchmark were run; source availability is not execution validation.

## Reviewed seven-architecture summary

**Problem:** crossing storage/input/accumulator/output formats changes element density, physical layouts, scale addressing and useful compute-width utilization. U003 covers those preparation and representation costs; U005 covers execution efficiency inside a reduction/vector operation. Fixed-width decomposition is one contributor, not a universal requirement: SVE is vector-length agnostic, and typed axis reductions also exist in other APIs.

| Approach / evidence layer | Mechanism and responsibility | Remaining costs after competent compilation |
| --- | --- | --- |
| Our Linx block ISA / API / TimingSim | Supported 2D typed Tiles encode geometry/layout/axis; backend sequences CELL microsteps. Software selects formats, scales and legal layouts; hardware/model manages mappings, admission, readiness and banks. | Numerical conversion, scale reduction/broadcast/traffic, packing/assembly, padded capacity, intermediate buffers and control remain. No automatic fusion or no-unroll claim; narrowing value-model TODO prevents a correctness claim. |
| NVIDIA PTX / library, Hopper versus Blackwell | Packed conversion; fixed matrix fragments and ownership; Blackwell native block scaling under type/layout constraints. Compiler can propagate layouts, fuse epilogues and amortize static weight preparation. | Required scale traffic, conversion and cross-owner exchange, padded tiles, shared-memory buffers, registers, synchronization and layout choices remain. Hopper WGMMA scale controls differ from native Blackwell block scaling. |
| Ascend public API / C intrinsic, generation-specific | Legal Cast/Quant pairs, ND/NZ/ZN movement and Cube/Fixpipe roles; newer MmadMx consumes constrained scale operands. Compiler/kernel chooses tiling and staged representation. | Conversion stages/double rounding, scale groups/traffic, layout movement, UB/L0 capacity and buffers, vector registers and pipeline synchronization remain. No arbitrary dtype pair or FP32→FP4 inference. |
| TPU Pallas / experimental API / public IR | Compiler maps supported dot precision, accumulator and output conversion to MXU/vector paths; generation controls legal formats/scaling. | Scale materialization, conversion/layout preparation, physical tiling/padding, VMEM buffers, vector intermediates and compiler scheduling choices remain; IR is not final ISA. |
| Tenstorrent API / Wormhole ISA | Unpack storage into SrcA/B, execute matrix/fidelity phases into Dst, pack to L1; explicit format state and CB ownership. BFP4 shares exponents and is not OCP FP4/INT4. | Unpack/pack and rounding, exponent/block organization, fidelity work, padded tiles, L1/CB buffers, Dst capacity and engine-state synchronization remain. |
| x86 AVX2 / AVX-512 ISA and intrinsics | Fixed 1D typed registers; conversion preserves an operation's element count, not necessarily destination register occupancy. Compiler can combine compatible packing, retain lane layout or unroll for reuse. | Necessary conversion/saturation, consumer-dependent permutations, scale arithmetic, masked/padded tails, live registers/spills, code size and width/extension dispatch remain; reduction intrinsic is not one opcode. |
| Arm NEON / SVE / SVE2 ISA and ACLE | NEON has fixed128-bit vectors; SVE uses VLA typed vectors and predicates. Narrowing bottom/top position rules and narrowing stores can avoid some packed-register work. Compiler chooses compatible layouts and loop decomposition. | Numerical conversion/scales, incompatible interleaving/ownership, predicates/tails, live registers/spills and scheduling remain. VLA does not promise full lanes; 1D reductions are not 2D axis Tiles. SME ZA is a separate boundary. |

Operations, physical movement, padding, intermediate buffer/register demand, scale representation, compiler choices and control must be evaluated for the same numerical workload at a stated interface layer. Track eliminated, amortized, hidden and remaining work separately. No PPA ranking or significant utilization/compiler-effort improvement is established. Detailed format evidence follows; [compiler review](U003-compiler-optimizations.md) defines the optimized baseline.

## Lowest-layer Linx operation format

The inspected Linx API emits typed block operations: TCVT uses `BSTART.TEPL 27` with source dtype, `B.DATR` destination dtype/rounding/layout, `B.DIM` geometry and `B.IOT` Tile operands. MX matrix paths use named `BSTART.CUBE TMATMULMX`; these are target-specific emission mechanisms, not the upstream A5 MLIR/API notation. [TCVT emitter](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/jcore/template_asm.hpp#L195), [typed operands/geometry](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/jcore/template_asm.hpp#L261), [MX operation](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/jcore/template_asm.hpp#L8306).

Rounding fields include selectable modes, but legal dtype pairs and saturation are conversion-contract specific; do not infer every mode works for every format. The current API deliberately rejects retired TQUANT/TDEQUANT calls and directs migration to matrix fixpipe postprocessing. Old comments describing FP32↔S8/U8 are not evidence of active standalone instructions. ## NVIDIA: PTX conversion and matrix paths

PTX is a virtual ISA, not final SASS. Keep storage format, matrix operand, accumulator and output separate.

| Representative path | Storage / operand | Accumulator / output | Scale and conversion boundary |
| --- | --- | --- | --- |
| FP32 → packed FP8, sm89+ | FP32 values → two E4M3 values in a16-bit carrier | No matrix accumulation implied | `cvt.rn.satfinite.e4m3x2.f32 p8, y1, y0;` uses nearest-even rounding and finite clamping. Input values must already have the intended scaling. |
| FP32 → packed FP4, supported Blackwell targets | FP32 values → two E2M1 values in an8-bit carrier | No matrix accumulation implied | `cvt.rn.satfinite.e2m1x2.f32 p4, y1, y0;` is conversion/packing, not a complete layout transform. The second source occupies the low byte/nibble in these packed forms. |
| Hopper WGMMA FP8 example | E4M3/E5M2 matrix operands in supported descriptor layouts | FP32 accumulator; final output conversion is separate | WGMMA sign controls are not quantization scales. Fence/commit/wait and layout preparation are separate obligations. |

Sources: [PTX cvt](https://docs.nvidia.com/cuda/parallel-thread-execution/#data-movement-and-conversion-instructions-cvt), [WGMMA](https://docs.nvidia.com/cuda/parallel-thread-execution/#asynchronous-warpgroup-level-matrix-instructions-wgmma-mma). Representative virtual instruction (surrounding synchronization omitted):

```ptx
wgmma.mma_async.sync.aligned.m64n8k32.f32.e4m3.e5m2 {d0,d1,d2,d3}, descA, descB, p, 1, 1;
```

Blackwell SM100 block-scaled paths add native scale operands subject to strict type/layout rules: NVFP4 uses UE4M3 scales for16-element blocks; MX families use UE8M0 for32-element blocks. SM120 has distinct `mma.sync` paths, so `tcgen05` cannot describe every Blackwell target. [CUTLASS functionality](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/blackwell_functionality.md). Hopper libraries can implement block scaling although WGMMA itself does not expose native block-scale operands. [cuBLAS narrow precision](https://docs.nvidia.com/cuda/cublas/index.html#narrow-precision-data-types-usage).

Per-tensor or per-row-A/per-column-B scaling may be factored outside a reduction when mathematically valid; scales varying across K blocks generally cannot collapse into one output multiply. Packing, swizzle/layout, scale traffic and final conversion remain costs. No PTX mnemonic alone establishes a complete efficient quantization pipeline.

## Tenstorrent: storage formats versus matrix execution

| Representative path | Storage / operand | Accumulator / output | Control boundary |
| --- | --- | --- | --- |
| Wormhole floating-point matrix | L1 storage → unpack SrcA/B; BF16/TF32 or FP16 matrix paths | BF16/FP32 Dst or FP16/FP32 Dst as supported; pack returns output to L1 | `fp32_dest_acc_en` selects Dst width, not all-FP32 arithmetic. |
| BFP8/BFP4 storage | Shared exponent per16 values; unpack expands into BF16/TF32 matrix inputs | Dst and pack-output format are separate choices | These are not E4M3/E2M1 FP formats or evidence of native INT4 matmul. |
| Wormhole integer path | INT8 with documented sign-magnitude restrictions | INT32 destination path | Do not equate its encoding indiscriminately with ordinary integer representations. |

Software initializes/reconfigures input format and matrix state, issues `matmul_tiles`, then packs Dst to the output buffer; surrounding CB ownership and synchronization are still required. Input `reconfig_data_format` and output `pack_reconfig_data_format` are separate controls, not arbitrary in-place quantization. [Compute engines](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/advanced_topics/compute_engines_and_dataflow_within_tensix.html), [matmul API](https://docs.tenstorrent.com/tt-metal/latest/tt-metalium/tt_metal/apis/kernel_apis/compute/matmul_tiles.html).

[MVMUL ISA](https://github.com/tenstorrent/tt-isa-documentation/blob/main/WormholeB0/TensixTile/TensixCoprocessor/MVMUL.md). TTNN BFLOAT8_B/BFLOAT4_B support is a storage/API claim; follow unpack format semantics before comparing matrix precision. [TTNN matmul](https://docs.tenstorrent.com/tt-metal/latest/ttnn/ttnn/api/ttnn.matmul.html), [unpack conversions](https://github.com/tenstorrent/tt-isa-documentation/blob/main/WormholeB0/TensixTile/TensixCoprocessor/Unpackers/FormatConversion.md).

[Pack conversion](https://github.com/tenstorrent/tt-isa-documentation/blob/main/WormholeB0/TensixTile/TensixCoprocessor/Packers/FormatConversion.md), [matrix unit](https://github.com/tenstorrent/tt-isa-documentation/blob/main/WormholeB0/TensixTile/TensixCoprocessor/MatrixUnit.md). ## x86: fixed vectors and consumer-dependent packing

AVX2/AVX-512 expose fixed-width one-dimensional typed vectors. For example, `VCVTPS2PH` converts16 FP32 elements in ZMM to16 FP16 elements in YMM; it preserves element count rather than filling a512-bit narrow destination. An AVX-512-FP16 path can use `VCVTTPH2W` for32 FP16→INT16 elements, then AVX-512BW `VPMOVSWB` for32 INT16→INT8 elements. This is integer conversion/saturating narrowing, not FP8 quantization: scaling, rounding/range and exception policy require a separate contract. [Intel instruction manual](https://cdrdv2-public.intel.com/789581/325383-sdm-vol-2abcd.pdf), [instruction updates](https://cdrdv2-public.intel.com/835748/252046-sdm-change-document.pdf).

AVX2 `VPACKSSWB` packs independently within128-bit lanes: for sixteen-word A/B, byte order is A[0:8], B[0:8], A[8:16], B[8:16]. A consumer requiring all A then all B needs rearrangement, whereas a compatible consumer can retain this layout. `_mm512_reduce_add_ps` expands to multiple instructions; its intrinsic name does not establish a single reduction opcode. [Intel permutation guide](https://builders.intel.com/docs/networkbuilders/intel-avx-512-permuting-data-within-and-between-avx-registers-technology-guide-1668169807.pdf). Compiler layout propagation, packed instructions and unrolling may remove or amortize particular work; remaining conversions, scale arithmetic, permutations, register pressure/spills and code size depend on the optimized consumer.

## Arm: NEON and scalable SVE are different contracts

NEON uses fixed128-bit vectors. Representative FP16→INT8 preparation uses `FCVTZS .8H` followed by `SQXTN .8B`; `SQXTN2` can fill the upper half from another source. `FCVTN`/`FCVTN2` narrow FP32→FP16; numerical scaling is separate. `vaddvq_f32` maps to two `FADDP` instructions rather than a 2D axis operation. [ACLE NEON intrinsic mappings](https://arm-software.github.io/acle/neon_intrinsics/advsimd.html).

SVE/SVE2 are vector-length agnostic: architectural vectors range from128 to2048 bits, with actual supported/configured lengths implementation-dependent. The supplied2025 introduction states powers of two; do not replace this with an arbitrary multiple-of128 promise. Typed 1D vectors, predicates and `FADDV`/`FADDA` reductions do not themselves encode a 2D Tile axis. [Introduction to SVE](https://documentation-service.arm.com/static/67ab35a4091bfc3e0a9478b5).

SVE FP32↔FP16 `FCVT` handles VL/32 elements, placing narrow results in the low half of32-bit positions. SVE2 bottom/top integer narrowing produces even/odd narrow positions: one INT16 source supplies VL/16 INT8 results; two sources can fill a vector but yield interleaving that the consumer must accept or rearrange. [SVE guide](https://documentation-service.arm.com/static/67e40f3398aa3c3b6eea6a85), [SVE2 guide, A5.1](https://documentation-service.arm.com/static/6659c722876c8d213b7870d3). `ST1B` can store low bytes directly from wider elements after numerical range requirements are satisfied, avoiding a separate packed register for suitable consumers. [SVE programming guide,6.3.2](https://documentation-service.arm.com/static/5f905515f86e16515cdc1a88).

Compatible layouts or narrowing stores can eliminate packing/permutation; VLA/predicates handle width portability and tails without guaranteeing full useful lane occupancy. Reuse-driven unrolling remains meaningful, with live-register/code-size costs. SME ZA belongs to a separate matrix architecture discussion and is not attributed to ordinary SVE.

## Variable Tile extents and the software/hardware boundary

Confirmed semantic distinction: **Tile shape/valid extent and capacity can vary without making instruction encoding variable-length**. Upstream PTO describes physical Rows/Cols, dtype/location/layout and meaningful valid rows/columns; these are not a promise of arbitrary shapes on every backend. [Pinned upstream programming model](https://github.com/PTO-ISA/pto-isa/blob/82361dd56d4ea5d0dc99f14028fe5eb8b5c46d19/docs/isa/programming-model/tiles-and-valid-regions.md).

A separate block-ISA specification was read from committed HEAD `a292fab1c852e87308da87cbbe181c6bc2cd263c`, rather than its in-progress local merge. `B.IOT` is a fixed32-bit header command recording ordered relative Local sources and renamed destinations, including a capacity code. This is not the upstream API's storage-address model. Local/Shared destination capacity domains are instruction-contract specific; a generic API enum range must not be treated as all legal Local bindings. Shared `B.IOS` describes core-wide Shared capacity separately. [B.IOT contract](https://github.com/PTO-ISA/pto-spec/blob/a292fab1c852e87308da87cbbe181c6bc2cd263c/docs/block/operands/B.IOT.md), [B.IOS contract](https://github.com/PTO-ISA/pto-spec/blob/a292fab1c852e87308da87cbbe181c6bc2cd263c/docs/block/operands/B.IOS.md).

The inspected Linx API separately carries compile-time physical Rows/Cols, dtype/layout storage size and static or runtime valid extents. It selects discrete capacity codes and imposes CUBE layout/row/element-width restrictions. Runtime valid extent is not unlimited runtime physical capacity. [Type/layout and size code](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/common/pto_tile.hpp#L944), [valid extent and capacity](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/common/pto_tile.hpp#L1034), [runtime-valid constructors](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/common/pto_tile.hpp#L1083).

**Qualified design benefit:** At the semantic operation boundary, a Tile instruction can describe work larger than one physical vector step. A backend/model can sequence the required microsteps, reducing the need to explicitly express every fixed-width chunk through compiler unroll-and-jam solely to match execution width. This is a division of responsibility, not measured compiler-complexity savings. The benchmark still contains explicitly unrolled loops and shape-specific tiling, conversion and assembly. [Actual FA loops](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/fa/fa_2d_unroll_gmma.hpp#L184), [packing/assembly](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/matmul/matmul_hif4_l1_quantize.hpp#L233).

Our TimingSim path splits vector work into fixed cell-sized operations while logical tags/mappings and physical binding handle variable payload spans and lifetimes. Capacity admission, bank arbitration, alias/generation/recovery and safe release remain hardware-model responsibilities. Current splitting has shape/stride/tail limitations; flexible semantic Tiles do not establish arbitrary full-shape support or a variable-width physical ALU. Layout/blocking, scale grouping, numerical conversion and packing remain software/ISA obligations.

## What packing and rearrangement actually do in this benchmark

Pinned SuperNPUBench revision remains `349c98964144dfd9ca6a2665eca5a16ca8f3e045`. “Shuffle” was an overly broad label: these examples use conversion, Tile assembly or transpose, not an identified GPU-style warp-shuffle instruction.

1. **HiF4X2 conversion versus Tile assembly.** The quantizer reads two32×32 FP32 halves, converts/scales BF16 intermediates and combines them into a32×64 BF16 Tile through `TileArray` / `TASSEMBLY`. That assembly joins logical fragments; it does not itself turn BF16 into4-bit data. A later `TCVT(data, scaled)` performs packed HiF4X2 conversion, storing two logical S1P2 values per byte; output addresses use N/2 and column/2 byte arithmetic. This is numerical-format packing plus this implementation's fragment strategy, not merely fixed-vector-width adaptation. A different direct path could avoid intermediate assembly; removing final packing while preserving the selected storage format is a different claim. [Types](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/matmul/matmul_hif4_l1_quantize.hpp#L43), [conversion/assembly/store](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/matmul/matmul_hif4_l1_quantize.hpp#L233).
2. **Low-precision Attention probability and scale payloads.** BF16 probabilities are normalized in32-column MX groups, converted directly into E2M1x2 fragment slots, and paired with E8M0 scale fragments. Separate `TASSEMBLY` calls produce P with logical shape32×Tk and PScale with valid shape32×(Tk/32); V has its own external data/scales. This prepares the numerical operands and scale organization needed by PV. It is not all removable lane rearrangement; source comments already identify an avoided extra packed-to-packed conversion. [Format contract](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/fa/fa_lowp.hpp#L12), [actual slots and assembly](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/fa/fa_lowp.hpp#L333).
3. **Transpose versus operand interpretation.** The transpose kernel defines input TileRows×TileCols and output TileCols×TileRows of the same DType, using TTRANS in a load/transpose/store path: actual matrix-layout work rather than quantization. [Shapes](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/transpose/detail/transpose.hpp#L294). In contrast, the FA QK/PV code uses matrix operand-layout options: natural K is interpreted as [N,K], V as [K,N] with `transpose_b`; this option does not by itself prove a separate transpose-copy instruction. [FA operand explanation](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/fa/fa_2d_unroll_gmma.hpp#L28).

Scale carrier geometry can also reflect hardware/API capacity constraints: the HiF4 example stores one valid E6M2 byte per row in a physical descriptor with two columns. That is distinct from the algorithm's one-scale-per-row/group rule. [Carrier explanation](https://github.com/PTO-ISA/SuperNPUBench/blob/349c98964144dfd9ca6a2665eca5a16ca8f3e045/benchmark/one-level-arch/kernels/basic_op/matmul/matmul_hif4_l1_quantize.hpp#L56). These examples do not establish INT4 packing or gather/permutation as part of the selected FA path; do not invent those operations. Optimization opportunities require separate evidence and are not evaluated here.

## Layout × format: verified M16/M32 boundary

Follow the chain **logical indices → blocked physical layout → element bits/packing → scale-group layout**. These are separate choices, not interchangeable names for a conversion. Linx API evidence remains pinned to `fac242a95bc70cd1783547555e5bd7335d1969bf`; model observations remain scoped to TimingSim `d5419b3e721df47daae02c38ef2a9b82187e5149`.

The API fixes CUBE cells at128 bytes. M16 has16 cell rows and M32 has32; cell columns are `128×8 / (cell_rows×element_bits)`. Hence FP32/FP16/FP8/FP4 cell-column counts are2/4/8/16 for M16 and1/2/4/8 for M32. This is physical geometry arithmetic, not an instruction throughput claim. Logical columns are rounded to cell columns, with capacity further rounded; valid extents remain distinct from padded physical storage. [Cell geometry/padding](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/common/pto_tile.hpp#L963).

For M layouts, the physical element index selects a cell from the logical column, then a row/column position inside that cell. M16's4-bit path additionally swaps local column groups; packing must follow that mapping rather than applying a naive row-major byte formula. Load/store layout codes distinguish ND↔M16/M32 materialized movement. [Index mapping and layout codes](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/common/pto_tile.hpp#L992).

The inspected vector path reads cell-sized payloads and has dtype-sensitive broadcast/reduction routing. Bank/port arbitration, allocation spans, alignment and padding are still resource constraints. Changing element width changes how many logical elements share a cell and can alter reduction/broadcast/scale addressing. Shape/stride/tail limitations in the current splitter prevent generalizing these supported paths to arbitrary tensors. Cell readiness is not proof of free layout conversion.

**Conceptual example, not a measured benchmark:** FP16 matrix input → FP32 accumulator → FP4+scale output requires deciding the accumulator's M-layout, reduction axis for scale generation, rounding/saturation, packed destination geometry and scale-group mapping. A direct supported conversion may preserve logical M-layout while changing cell columns; another producer/consumer layout may need explicit movement. Compiler layout/blocking and hardware cell/bank/capacity management remain coupled obligations. NVIDIA swizzle/fragment and Ascend ND/NZ/ZN counterparts will be compared only when their external layout-specific evidence is supplied.

## Typed axis reduction and conversion-width microsteps

A supported two-dimensional Tile carries dtype, layout and valid geometry, so a row/column reduction can express the logical axis rather than require application code to enumerate every physical lane mapping. In the inspected Linx API, `TROWSUM` encodes source dtype/layout and source geometry, deriving a one-column result; `TCOLSUM` derives one row and checks matching column geometry and fractal layout. These interfaces do not supply an independent wider accumulator dtype. Do not infer FP32 accumulation for an FP16 reduction from an FP32 matrix accumulator elsewhere. [Row interface](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/jcore/template_asm.hpp#L15090), [column interface](https://github.com/LinxISA/Linx-TileOP-API/blob/fac242a95bc70cd1783547555e5bd7335d1969bf/include/jcore/template_asm.hpp#L15742). Upstream Ascend PTO is a separate interface: its documented row/column sums require matching source/destination dtype and specific ND/DN layouts; scratch use differs by generation. Typed axis semantics are not exclusive to our design.

The current TimingSim row-reduction tree recognizes selected 32-bit profiles and packed FP16/BF16/INT16 profiles, with one or two elements per 32-bit word; 8-bit and narrower formats are not automatically admitted to that tree. Its dtype-specific element arithmetic does not establish arbitrary-layout or automatic widening support. This is U003 evidence about representation and axis mapping; tree throughput, reduction latency and internal utilization belong to U005.

For `TCVT`, the inspected splitter indexes microsteps by source CELL: supported widening maps one source CELL to multiple destination CELL writes; narrowing retargets multiple source steps into packed destination CELL addresses. **Important model limitation:** the narrowing source explicitly documents a remaining whole-CELL overwrite/value-model TODO, and the compute path does not implement TCVT numerical conversion. Address/footprint sequencing therefore is not validated packed-value correctness. The inspected byte-width mapping also does not establish every subbyte format or every FP8 path.

**Qualified design claim:** supported typed Tiles and hardware microstep sequencing may reduce explicit width decomposition and axis/layout mapping in application or compiler lowering. They do not prove automatic fusion of independent operations, hardware merging of multiple axes, complete lane use for FP16→FP8, arbitrary-layout conversion, or elimination of unrolling. Significant compiler-effort or utilization savings remain hypotheses requiring a matched worked example after competent compiler optimization. Numerical conversion, scale grouping, legal layouts, padding, intermediate assembly, destination readiness, banks/buffers and control remain costs; the actual benchmark conversion/assembly above remains part of the comparison.

## Common format and control-cost review

Compiler review: [layout and mixed-precision optimizations](U003-compiler-optimizations.md) separates eliminated, amortized, hidden and remaining costs; compare optimized implementations rather than naive sequences.

All seven approaches must manage representation and scale semantics before scheduling can help: dtype legality, input/accumulator/output precision, scale grouping, rounding/saturation, packed carrier addresses, layouts and producer/consumer ownership. Costs can include conversion instructions, reductions to derive scales, scale traffic, packing/assembly/shuffle/transpose, buffer capacity and engine-format/fidelity state. Equal bit width does not establish equal formats or arithmetic. Compare the same numerical task and abstraction level; no performance ratio or control-complexity winner is inferred.

## Current model boundary and comparison handoff

TimingSim contains dtype-aware matrix/scale paths, separate HiF4-word versus E8M0-byte scale handling and vector conversion routing that can widen into multiple destination cells. Presence of INT4/FP8 enum or routing cases is not comprehensive proof that all operand pairs, rounding modes or packing layouts execute correctly. Mixed-side scale support and exact legal profiles require their own pinned specification/implementation evidence.

Evaluate each architecture at the same level: storage, matrix inputs, accumulator and final output; scale granularity/type/layout; conversion rounding/saturation; packing, reordering/shuffle/transpose; operation Tile shape versus readiness/issue/data-transfer granularity. Dynamic scheduling may overlap eligible work, but does not remove representation conversion, scale traffic or packing. No quantitative layout-cost or utilization advantage is established here. All seven approaches are represented with distinct evidence layers.
